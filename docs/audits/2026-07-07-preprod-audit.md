# MAGE ID — Pre-Production Audit (2026-07-07)

**Method:** 16-domain multi-agent audit (45 agents), every P0/P1 adversarially verified, synthesized. See conversation for the workflow.

**Verdict:** NOT_READY

This build is NOT ready for a production ship. The audit surfaced a confirmed data-loss defect in the offline persistence layer (the app's core promise), multiple confirmed payment-correctness bugs that overcharge real clients or silently fail to reconcile captured money, two server-side security holes (SSRF in the vision relays and a missing ownership check that lets any account email another GC's homeowners), and several surfaces that ship polished "live" UI over non-functional stubs (a fake "Pay $X" RFP paywall that charges nothing, an orphaned Hire/messaging subsystem, a dead-end Post Job flow, demo videos that pop a developer alert, and a schedule-health KPI hardcoded to 0). Individually several of these are ship-blockers; collectively they represent systemic patterns (fail-open/charge-on-failure metering, unverified-JWT trust with no config.toml pinning, non-atomic read-modify-write, and client/server enforcement drift) rather than isolated bugs. A focused fix pass on the P0 set plus the highest-impact P1 correctness/security items is required before any customer-facing release.

---

## Top cross-cutting risks

- Non-atomic read-modify-write causing silent data loss recurs in at least three subsystems: the offline queue (stale-snapshot overwrite + no lock), the Stripe webhook's invoice.payments append (last-write-wins), and local project collections. Any concurrent or interleaved write can vanish with no error.
- Polished UI over non-functional stubs shipped as 'live': RFP-post paywall (fake charge), Hire jobs/workers/messaging (orphaned), Post Job (dead-end write with 'now live' toast), demo videos (dev alert), scheduler slip-vs-baseline KPI (hardcoded 0), and the materials location picker (decorative no-op). Erodes trust and, for the payment CTA, is a compliance risk.
- AI/vision metering is structurally unreliable: caps fail OPEN on any infra glitch (no server ceiling if a migration is unapplied), quota is charged BEFORE the model call so failures still bill the user, and four distinct features silently share one monthly counter — so quota, error copy, and cost protection are all wrong.
- Edge functions trust unverified JWT claims (bare decodeJwtPayload) for identity, tier, and master-email elevation, with no supabase/config.toml pinning verify_jwt:true. A single deploy toggle (or a copied function) grants full tier + master bypass, and reaches the SSRF surface. Appears in requireTier and award-rfp.
- Client/server and cross-surface enforcement drift from having two sources of truth: plan-review cap (client per-day vs server per-month, 30x), nav persona split (tab bar vs DesktopSidebar), invoice tax rate (stored vs current global setting), materials pricing (browse seed vs estimate seed; location picker vs settings.location), and marketing quota copy vs app AI_LIMITS.
- Trusting AI-reported numbers without deterministic reconciliation: the estimate wizard uses model subtotal/total/line-item math verbatim into client PDFs and project financials, and buyout commitments fold an AI 'leveled' comparison figure into the sub's committed cost that contradicts the signed subcontract.
- The offline-first invariant is not actually upheld: several core writes bypass supabaseWrite entirely (portal chat, engines), there is no reconnect trigger so the queue strands writes when signal returns with the app foregrounded, and drops are silent — directly contradicting the in-app 'will sync automatically' promise.

## P0 — ship blockers

### [offline-sync] Offline flush burns the retry budget and permanently deletes queued writes when the device is still offline
- **File:** `utils/offlineQueue.ts:124`
- **Fix:** In processGroup's catch, detect network errors with the same predicate supabaseWrite uses (lines 195-200) and do NOT increment retryCount for them — re-queue the mutation unchanged or abort the flush on first network error. Better: gate processOfflineQueue on actual connectivity (add @react-native-community/netinfo, bail if !isConnected). Reserve retryCount for genuine server 5xx. A field crew loses a day of DFRs/change orders after ~5 lock/unlock cycles offline, with no error shown.

### [payments-stripe] Stale Stripe pay link charges the original amount after an invoice edit or partial payment
- **File:** `app/invoice.tsx:411`
- **Fix:** Clear payLinkUrl/payLinkId (and ideally deactivate the old Stripe link) in handleSave when totalDue changes and in handleRecordPayment, so the next send regenerates a link for the current balanceDue. The immutable Price means a $10,000 link keeps charging $10,000 after a $4,000 payment or a downward edit — client is overcharged and the webhook marks it 'paid' past total.

### [project-core] Existing invoices re-total from the current global tax rate, not the rate stored on the invoice
- **File:** `app/invoice.tsx:284`
- **Fix:** Seed a taxRate state from existingInvoice?.taxRate ?? settings.taxRate ?? 7.5 (fall back to settings only for a brand-new invoice) and use that everywhere. The issued tax rate must be immutable. Otherwise changing the default rate in Settings silently changes an already-sent invoice's displayed total, its Stripe pay-link charge (Math.round(totalDue*100)), and the paid/partial threshold — and overwrites the stored total on Save.

### [payments-stripe] Stripe webhook returns 200 on a transient DB write failure, so the payment is never reconciled
- **File:** `supabase/functions/stripe-webhook/index.ts:463`
- **Fix:** Distinguish recoverable from permanent outcomes: return 500 (so Stripe retries with backoff) when reason is 'db update failed'; return 200 only for terminal cases ('duplicate', 'invoice not found', 'no metadata.invoice_id', payment_status not paid). The idempotency guard already makes a Stripe retry safe. Today a brief Supabase blip strands a captured payment as 'unpaid' forever with no alert.

### [payments-stripe] Connect direct-charge webhook events require a Connect-enabled endpoint — verify before ship
- **File:** `supabase/functions/create-payment-link/index.ts:391`
- **Fix:** Payment Links use the Stripe-Account header + application_fee_amount, making checkout.session.completed / account.updated / account.application.deauthorized connected-account events. Confirm the production Stripe dashboard endpoint has 'Listen to events on connected accounts' enabled (or is a Connect webhook) and is subscribed to all three events; add this to the deploy checklist and test end-to-end with a real connected-account payment. A standard endpoint receives none of these and NO invoice ever reconciles.

### [ai-relays] SSRF: vision functions fetch arbitrary client-supplied URLs server-side with no host allowlist
- **File:** `supabase/functions/analyze-drawings/index.ts:88`
- **Fix:** Before fetching pageUrls[]/photoUrls[] (analyze-drawings, analyze-photos, analyze-takeoff, compare-drawings), parse each URL and require an allowlisted host (the app's Supabase storage / signed-URL host). Reject non-https and private/loopback/link-local IP ranges with a generic 400 that does not echo the URL or upstream status. Today any paid account can probe internal services / cloud-metadata (169.254.169.254) and exfiltrate renderable bytes into Gemini.

### [notifications] homeowner-weekly-digest projectId branch has no ownership check — any authenticated user can email another GC's homeowners
- **File:** `supabase/functions/homeowner-weekly-digest/index.ts:463`
- **Fix:** Capture the VerifiedUser id from verifyUser(req) (cronAuth currently discards it) and, when the caller is not cron, require project.user_id === caller id before sendForProject; else 403. Apply the same owner check to morning-digest's userId branch. Project UUIDs are exposed in portal links, so today any account can email a victim's homeowners, burn Resend/Gemini quota, and suppress the legitimate Friday digest, with no rate limit.

### [bids-rfp] Homeowner RFP-post paywall is a non-functional stub presenting a fake 'Pay $X' charge
- **File:** `components/ClientPaywall.tsx:108`
- **Fix:** Do not ship the RFP-post fee as a live paid surface until real billing is wired. Either hide/disable the 'Pay to post' path (leave only subscription/free) or complete the Stripe payment-intent integration and move credit accounting server-side (RLS/edge-function enforced on the public_bids insert). Never show a 'Pay $X' CTA that records a local AsyncStorage credit without a charge — this collects zero revenue, is wiped on logout, is bypassable via direct insert, and is a likely-non-compliant purchase UI.

## Per-domain health

**routing-nav:** The routing layer is largely solid: all 110+ Stack.Screen registrations map to real files, there are no orphan/dead routes (every registered-but-un-navigated screen has inbound links), the mobile tab-bar and desktop Tabs screen registries are in sync (both register the same 12 tab routes), the rork-app:// deep-link handler and magic-link hash redemption are correct, and href:null is used deliberately for stable programmatic navigation. Two genuine navigation/gating inconsistencies exist, both P2: the DesktopSidebar's persona split diverges from the tab bar's (property_manager gets the full contractor rail on web but a minimal 2-tab bar on mobile), and the auth-redirect exemption meant only for the QuickBooks OAuth callback actually exempts the entire /integrations subtree from the login gate.

**auth-session:** Auth is broadly solid: session persistence via Supabase + AsyncStorage is correct, isLoading correctly gates the routing redirect so there's no unauthenticated flash, OAuth/Apple/password paths all consistently wipe local cache + clear the query client on sign-in, credential persistence is correctly refused on web (localStorage cleartext-password fix is in place), and the client OWNER_EMAILS list is genuinely in sync with server MASTER_EMAILS (both grant Business, verified against SubscriptionContext line 261). The magic-link edge function has proper per-email/per-IP throttling and doesn't leak account existence. The real gaps are: (1) the magic-link / password-reset deep-link redemption path skips the documented cross-tenant cache-wipe that every other sign-in path performs, and (2) biometric login silently breaks after a password change because stored credentials go stale. There's also one latent defense-in-depth footgun in the server tier gate.

**paywall-gating:** The core tier machinery is in good shape. Rank-based min-comparison is implemented correctly and consistently in all three places (useTierAccess.tierMeetsRequirement, useSubscriptionGate, and server requireTier all use free=0..enterprise=3 with >= / min-rank), so enterprise correctly satisfies lower gates and there is no off-by-one. MASTER_EMAILS (server) and OWNER_EMAILS (client) are in sync and both lowercase-compare. RevenueCat product ids (com.mageid.<tier>.<period>), package ids (<tier>_monthly/_annual), and entitlement names (pro/business/enterprise) are consistent across SubscriptionContext and the paywall. Every cost-bearing edge function (analyze-drawings/photos/takeoff/spec-book/compare-drawings, convert-pdf, ai text, analyze-plan-code) calls requireTier AND enforces a server-side MONTHLY_CAPS counter, so the expensive AI surface is not client-bypassable. The paywall AI_LIMITS table numbers all match LIMITS (daily/smart) and MONTHLY_CAPS (drawings/photos/takeoff), and ai_text monthly caps correctly equal daily×30. The one real defect is a period-unit mismatch on the Plan Review feature: the client gates it per-DAY while the server enforces the identical numbers per-MONTH, which silently breaks the Pro plan-review flow on any normal-size sheet set. A couple of dead/misleading config entries round out the list.

**offline-sync:** The offline queue has a sound-looking design (grouped ordering, terminal-error classification, bounded concurrency, Sentry/toast on hard failures) but three data-integrity defects undermine its core promise for a field app that markets "your work is saved and will sync automatically." (1) Flushing while still offline burns the per-mutation retry budget and permanently discards queued writes — the queue eats data after ~5 lock/unlock cycles with no signal. (2) Both the enqueue path and the flush path do non-atomic read-modify-write on a single AsyncStorage key with no lock, so a write enqueued during an in-flight flush (or two concurrent fire-and-forget writes) is silently clobbered. (3) There is no connectivity/reconnect trigger anywhere in the app (no NetInfo); the queue only drains on cold start and background→foreground, contradicting the pill copy that promises automatic sync "when you're back online." Additionally several core writes bypass supabaseWrite entirely and are not offline-resilient. Silent drops (retry-exhaustion and the 1000-item cap) never notify the user, unlike the non-network path which does. These are ship-blockers for an offline-first data-integrity guarantee.

**payments-stripe:** The Stripe integration is architecturally sound and shows real security maturity: server-side secret handling, HMAC-SHA256 webhook signature verification with replay protection and constant-time compare, per-session idempotency, JWT-derived ownership checks on create-payment-link/connect-onboarding/connect-status (closing the money-misrouting attack the comments describe), and a Connect deauthorization handler. The remaining risk is concentrated in a few money-correctness gaps rather than broken plumbing. The most important pre-ship issue is that a pay link is an immutable Stripe object tied to a fixed amount, but nothing invalidates it when the invoice's balance changes (edits or recorded partial payments), so clients can be charged a stale/wrong amount. Also verify the webhook endpoint is registered to receive events from connected accounts — because charges are direct charges on the GC's Express account, a standard platform webhook would silently never mark any invoice paid. Two smaller reconciliation/robustness gaps and a receipt-formatting bug round out the list.

**estimate:** The estimate/takeoff surface is well-structured (shared scope-question source of truth, robust Zod salvage in mageAI, server-side tier clamping on model selection, deterministic recompute in the takeoff-priced-estimate screen). But there are two real correctness/revenue issues to fix before prod: (1) the Quick Estimate Wizard renders and SAVES the AI's self-reported totals verbatim with zero arithmetic reconciliation, so line-total/subtotal/grand-total inconsistencies land on a client-facing estimate and PDF and are injected into project financials; and (2) the free-tier "1 free AI Takeoff" trial advertised by the client gate is a phantom — the server hard-blocks pro/business, so every free-user attempt still uploads and Cloudconvert-renders the PDF (real spend) before 403'ing, and never records the trial so it can be retried indefinitely. Two lower-severity metering/edge issues round it out. No crashes or unrecoverable data loss found (estimate overwrites are snapshotted to revisions).

**scheduler:** The scheduler is genuinely deep — a real forward/backward CPM engine with 4 dependency types, 8 anchor constraints, cycle detection, free/total float, calendar (working-day) awareness, a pure undo/redo reducer, and correctly-metered AI copilot. The undo/redo reducer (utils/scheduleHistory.ts) is pure and correct. scheduleCopilot metering (checkAILimit → record-on-success only) is sound, with a server-side monthly-cap backstop in the ai edge function, so there's no free-tier revenue bypass. Drag-to-create-dependency validates cycles during the drag and only commits when valid. However, two real problems will surface on nearly every production schedule: (1) three of the four dependency types (FF, SF, SS) compute their finish↔start conversion using RAW calendar-day duration arithmetic while the rest of the engine walks working days — and the default schedule is a 5-day work week, so non-FS links land on wrong dates and produce a wrong critical path/float; (2) the Dashboard/Header "slip vs baseline" KPI is hardcoded to 0, so a slipped project always reads "On baseline." Total/free float are also reported in calendar days rather than working days. No crashes or data-loss found in this domain.

**materials:** CATEGORY_META is healthy post-emoji-removal — all 17 real categories have color/iconName/label entries, every iconName resolves to a Lucide component in both consumer maps with a Package fallback, and PRICE_VOLATILITY covers every category. The cart context itself (add/remove/persist/dedup/markup) is sound: dedup-by-id, hydration guard against clobbering persisted state, defensive shape-cleaning on load, and correct bulk/markup math downstream. The serious issues are upstream in the data the browse renders: getLivePrices returns the fully EXPANDED catalog (274 base products x 73 regional/tier/assembly variants = ~20,000 rows), and the Materials browse screens render all of them, so a category detail shows ~1,600 near-duplicate rows and the header claims "20,002 MATERIALS." The prominent location picker on the Materials tab is decorative — it never reaches the detail list, the cart, or the estimate. And the headline price shown on browse cards is the bulk price the user usually won't qualify for.

**bids-rfp:** The RFP-award server path is genuinely solid: the award-rfp edge function delegates to a SECURITY DEFINER Postgres RPC (verified present in prod) that atomically enforces ownership, "already-awarded", and response-belongs-to-bid, so the marketplace award flow is safe from partial-state corruption. The buyout dashboard/leveling UI is well-built with good defensive guards (zero-bid refusal, package-mismatch refusal, allowance-lock snapshotting). Two real pre-prod issues stand out: (1) the buyout Commitment amount and savings are stamped from the AI "leveled total" rather than the actual bid the sub gave — inflating committed cost and contradicting the subcontract PDF the sub signs; and (2) the homeowner RFP-post paywall is a non-functional stub that shows a "Pay $X" button but collects no money and stores credits only in AsyncStorage. Plus a few medium correctness/UX gaps around a non-unique estimate-item key, an owner-gate that fails closed on a slow query, and an unverified JWT decode in the award edge fn.

**project-core:** The Project domain is broadly solid: every tertiary_* collection has a consistent add/update/delete + getForProject shape, writes flow through the offline queue, and optimistic local state is persisted before sync. The context is enormous but disciplined. However there are a few real pre-production defects. The most serious is a money-integrity bug: the invoice editor always recomputes tax/total from the current global settings.taxRate rather than the taxRate stored on the invoice, so any historical invoice silently re-totals (and its Stripe pay-link charges a different amount) after the GC changes their tax rate. Secondary issues: project deletion does not cascade-clean local sub-collections (orphaned unpaid invoices keep inflating global A/R), change-order numbering uses length+1 and produces duplicate CO numbers after a deletion, and the universal "cloud returned empty -> fall back to local" query pattern can resurrect deleted records across devices. None are crashes, but the invoice tax bug is embarrassing/revenue-affecting and should be fixed before ship.

**portal:** The portal is in good shape post-redesign: data-bindings are intact (all JS getElementById targets exist in the static markup), the anon-RPC payloads (portal_choose_selection, portal_sign_contract, change_order_approvals, portal_messages, portal_budget_proposals) match their server-side migration signatures, and the passcode gate + two-stage (hash → server snapshot → expired-fallback) load flow are correct. The reskin's class renames left one stale spot in the closeout-binder print CSS, causing non-binder chrome to leak into the printed "permanent record." A minor unescaped-interpolation issue exists in the budget greeting. No crashes, no data loss, no tier/paywall or money-calc defects found in this domain.

**ai-relays:** The AI/vision suite has a genuinely thoughtful defense-in-depth story — every paid edge function now calls requireTier, per-tier MONTHLY_CAPS are enforced server-side, prompt/schema/token size caps guard against cost-bomb prompts in /ai, and convert-pdf does real per-page metering with IDOR/ownership checks. The gaps are in the failure and consistency modes, not the happy path. The most important pre-prod issues: (1) the sole server-side cost ceiling fails OPEN on any metering-RPC error, so an unapplied migration or a DB hiccup silently un-caps every AI/vision endpoint; (2) all five vision functions fetch arbitrary client-supplied URLs with no host allowlist, an authenticated SSRF/probe primitive that also leaks upstream status codes. Secondary: four separate paid features share one 'analyze_drawings' counter (wrong quota + wrong error copy), and /ai + two vision functions charge the monthly counter before the Gemini call so failures burn paid quota — inconsistent with the correct post-success metering already used in analyze-plan-code and convert-pdf. Finally, requireTier trusts unsigned JWT claims (including the master-email elevation) and there's no config.toml pinning verify_jwt:true, so one bad deploy would collapse the whole gate. None are guaranteed crashes today, but the fail-open caps and SSRF should be closed before shipping.

**notifications:** The notification/digest layer is largely solid: the notify dispatcher fails closed on privilege determination, honors both the notification_preferences table and the is_email_unsubscribed suppression table before every email, and the homeowner-weekly-digest's pre-send unsubscribe guard (the explicit FOCUS item) is implemented correctly — it checks isEmailUnsubscribed per invite, `continue`s on suppression, and only stamps lastSentAt when at least one email actually sent, so an all-suppressed project loses nothing and won't be marked done. Two real defects hurt the weekly digest: (1) the "Send preview" button stamps lastSentAt, which then suppresses the very next scheduled Friday cron send for that project, and (2) the projectId branch has no ownership check, so any authenticated user can trigger digest emails to a third party's homeowner invites. A third, lower-severity issue is audit-log corruption in the bid_question_answered fan-out. No crashes or paywall bypasses found in this domain.

**companies-hire:** This domain ships two parallel, disconnected systems and the seams show badly. The Discover surfaces (discover/hire.tsx, discover/companies.tsx) read external-scrape tables (cached_jobs, cached_companies) and open external apply/website links, while the entire in-app Hire subsystem (HireContext + job-detail, worker-detail, post-job, messages, and CompaniesContext) reads separate tables (job_listings, worker_profiles, companies, conversations) that no list screen ever surfaces. The net effect: posting a job silently goes nowhere despite a "now live" confirmation; the job/worker/messaging feature set is reachable only via a circular link between two detail screens and cannot create worker profiles at all; and "your company" is derived from an unfiltered, globally-readable companies table so outbound bids and verification requests can be branded with a stranger's company name. Discover also shows hardcoded vanity counts (2957/869/1317) that contradict the empty states one tap away. None of this is a crash, but multiple visible flows are non-functional or misleading and should not ship as-is.

**marketing-site:** The marketing site is largely solid: internal links resolve, OG/favicon/screenshot assets all exist, the margin calculator math is correct, meta/SEO/OG tags and JSON-LD are well-formed, and the Fraunces heading wiring is intact in both stylesheets. However there are two real pre-production problems. (1) The mobile header navigation is completely dead on every page except the homepage: styles.css hides the nav at <=720px, but the shared hamburger script only activates for `.nav-links` while all styles.css pages use `.links`, and styles.css has no `.nav-toggle` rule at all — so phone visitors (the primary audience) get no header nav across pricing, demo, features, compare, and every alternative/legal page. (2) The demo page — the destination of the homepage's "See how it works (90 sec)" CTA — ships placeholder video players whose click handler pops a developer-facing `alert('Video coming soon — record + upload...')`. Beyond those, there are pricing/brand accuracy inconsistencies (an App Store CTA that contradicts the homepage's deliberate removal, a Space-Grotesk vs Fraunces heading mismatch in the homepage "moat" section, a Business PDF-cap number that disagrees with the app, and redundant tier feature listings).

**design-consistency:** The token system itself is well-built and broadly adopted — constants/designTokens.ts (spacing/radius/shadow/motion) is imported by 270 files, constants/colors.ts uses theme-aware getters, and the anti-slop cleanup was thorough (zero UI emoji, only 5 LinearGradient files all in legit onboarding/hero contexts, no rainbow palette).
