## Findings (ranked; most severe first)

### F1 — [P1] [CONFIRMED] Cold start is gated on four un-timed network round-trips even when a complete local cache exists; a stalled (not failed) connection shows the crane loader for up to ~60 s.
- Where: `app/_layout.tsx:546-551` (gate), `:358` (source of `projectLoading`);
  `contexts/ProjectContext.tsx:5512` (what `isLoading` means), `:559-612` (projectsQuery),
  `:638-676` (settingsQuery), `:1676-1698` (userRoleQuery), `:186-199` (loadLocal/saveLocal);
  `lib/supabase.ts:36-43` (no global fetch timeout).
- Evidence:
  - `_layout.tsx:546-551`: `const bootstrapping = authLoading || projectLoading || hasSeenOnboarding === null; if (bootstrapping) { return <CraneLoader label="MAGE ID" />; }`
  - `ProjectContext.tsx:5512`: `isLoading: projectsQuery.isLoading || settingsQuery.isLoading || onboardingQuery.isLoading || userRoleQuery.isLoading`
  - `ProjectContext.tsx:559-612` projectsQuery: `if (canSync) { try { const { data, error } = await supabase.from('projects').select('*').order(...)` → `await supabase.from('project_financials').select('*')` → `const localForMerge = await loadLocal<Project[]>(PROJECTS_KEY, [])` → `await saveLocal(PROJECTS_KEY, merged); return merged;` — the local copy is returned **only** in the `catch`/non-sync branch (`return loadLocal<Project[]>(PROJECTS_KEY, [])`).
  - `settingsQuery` (`:644`) `supabase.from('profiles').select('*')` and `userRoleQuery` (`:1681`) `supabase.from('profiles').select('user_role')` follow the same network-first shape.
  - `createClient(...)` in `lib/supabase.ts:36-43` sets `auth` options only; no `global.fetch` wrapper, no `AbortSignal`. supabase-js PostgREST calls therefore inherit the platform default (iOS URLSession ≈ 60 s per request).
- Startup path, in order (what gates first paint): native splash → `useFonts` (5 bundled faces, `:1366-1372`) or a 1.2 s failsafe (`:1395-1399`) → `BrandSplash` (~1 s animation, app mounts underneath) → `CraneLoader` until (a) `supabase.auth.getSession()` (AsyncStorage) resolves, (b) `projects` + `project_financials` HTTP round-trips complete, (c) the previous `mageid_projects` blob is JSON-parsed (`loadLocal`), (d) the merged array is JSON-stringified and written back (`saveLocal`), (e) `profiles.select('*')` (which carries the 228 kB logo, see F5) and `profiles.select('user_role')` complete. RevenueCat `configure/getCustomerInfo/getOfferings` (`SubscriptionContext.tsx:101-160, 276`) do **not** gate paint — correct. The other 28 ProjectContext queries, SafetyContext's 7 `hydrateCollection` selects, Crew/Wip/Scan/Bids/Companies (5) and the notification feed all fire in parallel in the same first second (≈50 HTTPS requests, ≈45 AsyncStorage writes).
- Failure scenario: a superintendent opens the app in a basement/elevator/tower-handoff state where the LTE link is associated but stalled. `fetch` neither succeeds nor rejects; the crane loader stays up until the OS times the request out (≈60 s on iOS), then the `catch` finally returns the local cache. Airplane mode is fine (rejects fast). The same happens on web. Every collection was already on disk the whole time.
- Fix: hydrate from disk first and refresh behind the UI — either a react-query AsyncStorage persister (`persistQueryClient`) so `isLoading` is false on hydration and the network run is `isFetching`, or `placeholderData`/`initialData` from a one-time `AsyncStorage.multiGet` of the four boot keys; wrap the boot-path requests in `AbortSignal.timeout(8_000)` and fall through to the local copy on abort; gate `bootstrapping` on "hydrated from disk", not "server answered".
- Effort: M (S for the timeout-only mitigation).

- Evidence:
  - Counts across `ProjectContext.tsx`: `select('*')` 46 sites; `.eq('user_id'` **0**; `.eq('project_id'` **0**; `.limit(` **0**; `.range(` **0**. Every collection is fetched whole, for every project, with every column (jsonb blobs included: `projects.schedule/estimate/estimate_versions/linked_estimate/scope`, `daily_reports.manpower/materials_delivered/work_progress/photos`, `change_orders.line_items/audit_trail`, `invoices.line_items/payments`).

- Fix: (1) tenant-filter and column-select every boot query (`.or(\`user_id.eq.${userId},project_id.in.(${collabProjectIds})\`)`; select only the columns the mapper uses — schedules/estimates on the project list are the 90% of bytes and are needed only on the detail/schedule screens); (2) page or scope the big three (photos and DFRs by project or "last 90 days" with on-demand backfill; `estimate_versions` lazy); (3) stop writing AsyncStorage inside queryFns — persist once through a query persister; (4) cache signed URLs in AsyncStorage keyed by `storagePath` with expiry and sign only misses.
- Effort: M.

- Where: `package.json` (no `expo-image-manipulator`), 42 `ImagePicker.launch*` sites (e.g. `app/daily-report.tsx:492, :523, :532`, `app/project-detail.tsx:1016-1020`, `app/punch-walk.tsx:247-254`), `utils/storage.ts:19, :73-90` (signing, no transform), `utils/fileBytes.ts:31-60` (base64 → bytes), `utils/photoUploadQueue.ts:335` (`MAX_CONCURRENCY = 2`), `app/project-detail.tsx:3663-3673, :3730, :3736` (grid), `hooks`/components image usage.
- Evidence:

The only size control anywhere is the picker's `quality: 0.4-1.0` (JPEG re-encode at native resolution; `app/plans.tsx:94` and `app/area-takeoff.tsx:252` use `quality: 1.0`).
  - `utils/storage.ts:81` `.createSignedUrls(chunk, PHOTO_URL_TTL_SECONDS)` — no `transform`; nothing in `photoUploadCore.ts`/`photoUploadQueue.ts` produces a thumbnail.
  - `app/project-detail.tsx:3663-3673`: `const renderThumb = (photo: ProjectPhoto) => (<TouchableOpacity key={photo.id} style={styles.photoThumb} ...> <Image source={{ uri: photo.uri }} style={styles.photoThumbImage} resizeMode="cover" />` rendered by `:3736 {searched.map(photo => renderThumb(photo))}` (and `:3730` per day-group) inside the section modal's `ScrollView` — `project-detail.tsx` has 7 `<ScrollView` and 0 `<FlatList`. `searched` is the whole tag/search-filtered collection; no slice.

- Effort: M.

### F6 — [P2 now, P1 at ~100 tenants] [CONFIRMED] RLS predicates are evaluated per row with no tenant filter from the client: 301 of 337 policies re-run `auth.uid()` per row and 47 call `can_access_project()` per row (measured 20 µs/call), and boot queries seq-scan every tenant's rows.
- Where: `supabase/schema.sql:4019-4032` (`can_access_project(uuid)`), `:4586-4600` (`is_project_collaborator`), section 5 policies (e.g. `daily_reports_collab_select`, `photos_collab_select`, `projects_select`); client `contexts/ProjectContext.tsx` (no `.eq('user_id')`, see F2); Supabase performance advisors.
- Evidence:
  - Functions are `STABLE SECURITY DEFINER SET search_path = 'public'` (good); `can_access_project` = `exists(select 1 from projects p where p.id = pid and p.user_id = auth.uid()) or exists(select 1 from project_collaborators pc where pc.project_id = pid and pc.user_id = auth.uid() and pc.status = 'accepted' and …)` — two sub-selects per call, hitting `projects_pkey` and `idx_project_collaborators_project` (`idx_project_collaborators_user` has idx_scan = 0).
  - Policy shapes (pg_policies): `daily_reports_collab_select`: `((auth.uid() = user_id) OR can_access_project(project_id))`; `photos_collab_select` identical; `projects_select`: `((auth.uid() = user_id) OR is_project_collaborator(id))`. The `OR <function>` defeats `idx_*_user_id`.
  - `EXPLAIN ANALYZE` as the heaviest tenant: `projects` → `Seq Scan on projects … Filter: ((… = user_id) OR is_project_collaborator(id, 'viewer')) Rows Removed by Filter: 4` (19.6 ms cold / 1.2 ms warm for `daily_reports`); `daily_reports` → `Seq Scan … OR can_access_project(project_id, 'viewer') Rows Removed by Filter: 3`.

  - Counts: 337 policies on 105 tables; **301** with unwrapped `auth.uid()`; **47** using `can_access_project`; advisors: 309 × `auth_rls_initplan` WARN, 325 × `multiple_permissive_policies` WARN (e.g. `profiles_select` + `profiles_select_own`, `projects_insert` + `projects_insert_own`, `projects_delete` + `projects_delete_own`; 24 each on `change_orders/contacts/equipment/invoices/price_alerts/subcontractors/user_tracked_bids`).

At 100 tenants shaped like the brief's account, `photos` ≈ 200K rows → ≈ **4 s of DB CPU per user per boot** for that one query (estimate), repeated for every table with a `can_access_project` policy; today (7 projects) it is 1-20 ms and invisible.
- Failure scenario: cold-start time and DB CPU grow with the number of *other* customers, not with the user's own data; on the shared compute tier this also inflates every other request's latency.
- Fix: (1) wrap `auth.uid()` as `(select auth.uid())` in all policies (mechanical; the advisor lists them); (2) client: add the tenant filter (`.or('user_id.eq.<uid>,project_id.in.(<collab ids>)')`) so `idx_*_user_id` is usable and foreign rows are never visited; (3) rewrite the collaborator branch as `project_id IN (SELECT project_id FROM project_collaborators WHERE user_id = (select auth.uid()) AND status = 'accepted')` — evaluated once as a hashed sub-plan instead of per row; (4) merge the duplicated permissive policies. Regenerate `schema.sql` and update `validate-rls-write-leaks`.
