## Findings (ranked; most severe first)

### F1 — P1 CONFIRMED — Every GC notification that originates from a database trigger is silently rejected by the deployed `notify` function, because `app_config.notify_key` is empty and the triggers therefore call `notify` as an anonymous caller
- Where: `supabase/schema.sql:4296-4329` (`fire_notify`), `:4687-4707` (`notify_portal_message_fn`), `:3661,3682,3685,3702,3703` (the five AFTER triggers); deployed `notify` v19 lines 220-226 and 938-942 (identical to repo `supabase/functions/notify/index.ts:220-226, 938-942`); production `app_config.notify_key` length 0.
- Evidence:
  - `fire_notify` builds `'Authorization', 'Bearer ' || COALESCE(v_key, '')` and `'apikey', COALESCE(v_key, '')` (schema.sql:4314-4317). Production: `select length(value) from app_config where key='notify_key'` → `0`. So the header is literally `Bearer ` with nothing after it.
  - `notify_portal_message_fn` posts with `headers := '{"Content-Type": "application/json"}'` — no credential at all (schema.sql:4696).
  - Deployed `notify` (v19, `verify_jwt:false`): `isPrivileged = isServiceRoleToken(bearer) || isServiceRoleToken(apikey) || (await verifyUser(req)) !== null; const isAnonCaller = !isPrivileged;` — `isServiceRoleToken('')` is `!!token && …` → false; `verifyUserToken('')` returns null for `token.length < 20`. Then `dispatch`: `if (isAnonCaller && !ANON_ALLOWED_EVENTS.has(event)) return { ok: false, reason: 'event_not_anon_allowed', event };` with `ANON_ALLOWED_EVENTS = {contract_signed, selection_chosen, bid_question_asked, bid_question_answered, closeout_binder_sent}`.
  - The trigger-fired events are `co_approval` (trg_notify_co_approval), `budget_proposal` (trg_notify_budget_proposal), `sub_invoice_submitted` (trg_notify_sub_invoice), `sub_invoice_reviewed` (trg_notify_sub_invoice_reviewed) and `portal_message` (notify_portal_message_fn). None is in the allowlist.
  - No other path delivers them: the app's `utils/notifyClient.ts` is only called for `closeout_binder_sent`, `bid_question_asked`, `bid_question_answered`; the static portal's `notifyEvent()` (`marketing/portal/index.html:3610-3623`) uses the anon key and sends `portal_reaction`. `fire_notify` swallows every outcome (`EXCEPTION WHEN OTHERS THEN RAISE NOTICE`), and pg_net returns the 200 `{ok:false}` body to nobody.
  - `docs/security/2026-07-21-anon-read-audit.md:26` recorded the key as "an empty `notify_key`… No secret today" and drew no consequence; `grant_fire_notify_to_anon.sql:14-15` describes fire_notify as posting "with the configured notify_key" — it was never configured.
- Failure scenario: a homeowner e-signs a change order in the portal (`portal_submit_co_approval_signed` → INSERT `change_order_approvals` → trigger). The GC gets no push, no email, and no `notification_outbox` row (that row is written by `notify`'s `dispatchOne`, which never runs). The same for a client budget proposal, a client portal message, a sub-portal invoice submission, and the sub's "your invoice was approved/rejected/paid" email. Three portals are enabled in production today. Only the 90-second poller / realtime subscription in the app reveals the event, so the GC learns about a signed CO only when they happen to open the app.
- Fix (smallest correct): make the trigger path privileged the way `public_bids_notify_nearby_fn` already is — it sends `'x-cron-secret', (select secret from private.cron_auth limit 1)` (schema.sql:5130-5133). (1) In `notify`, treat a request whose `x-cron-secret` header satisfies `verify_cron_secret` as privileged (one `||` term next to `isServiceRoleToken`). (2) Rewrite `fire_notify` and `notify_portal_message_fn` to send that header instead of the empty bearer; both are SECURITY DEFINER so they can read `private.cron_auth`. (3) Do not put the service-role key into `app_config` — it is a table anon holds INSERT/UPDATE grants on (RLS blocks today, but the key would sit one policy away from exposure). Then revoke `fire_notify` from `anon, authenticated` (see F9); it no longer needs to be caller-executable once the trigger functions that call it are themselves SECURITY DEFINER.
- Effort: S (one migration + one edge-function line + redeploy `notify`).

### F2 — P1 CONFIRMED — The `field` collaborator role does not exist in production: the CHECK constraint rejects it, `can_access_project` has no `field` tier, the deployed `project-invite` rejects it, and `DEPLOY-VERIFIED-2026-09-02.md` says the migration "IS applied"
- Where: production `project_collaborators_role_check`; `supabase/schema.sql:2276, 4019-4032, 4586-4599`; deployed `project-invite` v1 (`ROLES = new Set(["owner","editor","viewer"])`); repo `supabase/functions/project-invite/index.ts:218-220` (accepts `field`); `components/collaborators/CollaboratorsManager.tsx:35,146`; `DEPLOY-VERIFIED-2026-09-02.md:107`.
- Evidence (live, queried today):
  - `pg_get_constraintdef` → `CHECK ((role = ANY (ARRAY['owner'::text, 'editor'::text, 'viewer'::text])))`.
  - `can_access_project(uuid)` body → `… and case min_role when 'editor' then pc.role in ('owner','editor') else true end` — no `when 'field'` branch. `is_project_collaborator` (schema.sql:4597) is identical.
  - `DEPLOY-VERIFIED-2026-09-02.md:107`: "`can_access_project()` (2 overloads) | `20260826130000_field_role` IS applied". That was verified by existence of the two overloads; the migration file itself says the text overload "exists in production but was created OUT OF BAND" (`20260826130000_field_role.sql:101-106`), so existence proves nothing. The migration's other visible effects — the widened CHECK and the 8 field-table write policies moving from the `editor` to the `field` tier — are absent: `daily_reports_collab_insert` etc. still say `can_access_project(project_id, 'editor'::text)` (schema.sql:3046).
  - `project_collaborators` has 0 rows in production, so no invite has ever exercised any role.
- Failure scenario (traced through deployed code): GC opens Collaborators, picks "Field — Schedule & field work — no costs or margins", taps Invite → `POST /functions/v1/project-invite {action:'invite', role:'field'}` → deployed v1 returns 400 `"projectId, a valid email, and role (editor|viewer) are required"`. Either way the role the product sells as its crew on-ramp cannot be granted, and everything built on it (`project_financials` split, `can_view_project_financials` excluding `'field'`, `utils/roleBlinding`, the free `field` seat in `utils/seatModel.ts`) is inert.
- Second consequence — role inversion in the 09-03 feature batch: six policies were written against the `field` tier that does not exist — `access_reservations_collab_insert/_update`, `building_access_rules_collab_insert/_update`, `deliveries_collab_insert/_update` all use `can_access_project(project_id, 'field'::text)` (schema.sql:2830-2835, 2889-2894, 3062-3067). In production that resolves through the `else true` branch, i.e. **any accepted collaborator including a Viewer** ("Read-only, sees financials", `roleBlinding.ts:57`). Exact call, with a viewer's JWT: `POST /rest/v1/deliveries {"id":"<uuid>","user_id":"<viewer uid>","project_id":"<pid>","status":"scheduled",…}` → 201. The migration comment at `20260826130000_field_role.sql:92-94` says the field tier "Deliberately EXCLUDES 'viewer'"; the live database includes them.
- What a field collaborator could read today if the migration were applied without phase 2: the full `projects` row (`estimate`, `linked_estimate`, `estimate_versions`, `target_budget`, `client_portal` incl. credentials, `calendar_token`, `scope`, `schedule`) and, via `can_access_project(project_id)` default tier, `access_reservations, building_access_rules, daily_reports, deliveries, drawing_pins, field_tickets, permits, photos, plan_calibrations, plan_markups, plan_sheets, punch_items, rfis, submittals, time_entries`. Of these, money lives in `projects.*` (legacy jsonb) and in `field_tickets` (`labor`/`materials`/`equipment` jsonb with rates plus `markup_percent`, schema.sql:883-887) — the latter is not covered by the phase-2 drop at all. Not readable: `project_financials`, `invoices`, `change_orders`, `commitments`, `aia_pay_apps`, `lien_waivers`, `draw_periods`, `wip_periods`, `workers.hourly_rate`, `sub_submitted_invoices`, `project_contracts`.
- Fix: apply `20260826130000_field_role.sql` (re-verify its 8 policy names against today's `pg_policies` first — the file was checked on 08-26, before the 09-02/09-03 batches), redeploy `project-invite` from the repo, and correct `DEPLOY-VERIFIED-2026-09-02.md:107`. Add a guard `scripts/validate-role-tiers.ts` that parses schema.sql and fails when (a) the role CHECK omits a role the client offers (`CollaboratorsManager.tsx`/`projectRole.ts`), or (b) any policy passes a `min_role` literal that `can_access_project`'s body has no `when` branch for — rule 5: enumerate the literals, do not list them.
- Effort: S to apply; S for the guard.

### F3 — P1 CONFIRMED — The client-portal passcode is enforced only by the HTML gate; every data RPC accepts the link token alone, and `portal_sign_contract` skips the passcode whenever the caller passes NULL — which is what the shipped portal always does
- Where: `supabase/schema.sql:4809-4840` (`portal_get_snapshot_v2`), `:4776-4793`, `:4876-4894`, `:4991-5032`, `:5034-5100`, `:4733-4774` (no `p_passcode` parameter at all); `:4943-4989` (`portal_sign_contract`); `marketing/portal/index.html:3793`; `utils/portalSnapshot.ts:121-125`; `app/client-portal-setup.tsx:975`.
- Evidence:
  - `portal_sign_contract`: `if p_passcode is not null and coalesce(v_portal->>'passcode','') <> '' and p_passcode <> (v_portal->>'passcode') then raise exception 'sign_denied'` — a NULL `p_passcode` skips the whole check even when `requirePasscode` is true.
  - The portal calls it with `p_passcode: (data && data.passcode) || null` (`portal/index.html:3793`) and the snapshot "passcode is intentionally NOT serialized" (`utils/portalSnapshot.ts:121`) — so the argument is always NULL.
  - `portal_get_snapshot_v2`, `portal_get_messages`, `portal_post_message`, `portal_submit_budget_proposal`, `portal_submit_co_approval`, `portal_submit_co_approval_signed`, `portal_choose_selection` check only `portal_project_for_token(p_portal_id, p_access_token)`.
  - The GC is told: "Require clients to enter a passcode before viewing the portal. Share it separately from the link." (`client-portal-setup.tsx:975`). The deployed `validate-portal-passcode` v7 (lines 30-33) documents the opposite design: "the passcode is a SECONDARY control".
- Failure scenario: the invite email is forwarded (the case the passcode exists for). The recipient runs `POST /rest/v1/rpc/portal_get_snapshot_v2 {"p_portal_id":"<id>","p_access_token":"<t from the link>"}` with the anon key and receives the full snapshot; then `POST /rest/v1/rpc/portal_submit_co_approval_signed {…,"p_decision":"approved","p_consent_accepted":true,…}` and a signed approval is recorded. The GC believes the passcode gate stopped this. 0 of the 3 live portals have a passcode set today, so exposure is a promise gap, not a live leak.
- Fix: add `p_passcode text default null` to every portal RPC through one shared `portal_authorize(p_portal_id, p_access_token, p_passcode)` that raises when `coalesce((client_portal->>'requirePasscode')::boolean,false)` and the passcode does not match; store the passcode hashed (`crypt()`/`digest`) once F4 moves it out of the row. Until then, at minimum change the copy to say the passcode protects the page, not the data.
- Effort: M.

### F4 — P1 CONFIRMED — Any accepted collaborator (viewer or editor; field once it exists) can read the client portal's `accessToken` and plaintext `passcode` from the `projects` row and act as the client, including e-signing change orders
- Where: `supabase/schema.sql:3421-3422` (`projects_select`), `:1529` (`client_portal jsonb`), `:4896-4908` (`portal_project_for_token` reads `client_portal->>'accessToken'`), `:4967-4970` (plaintext passcode compare), deployed `validate-portal-passcode` v7 line 134 (`constantTimeEqual(passcode, portal.passcode)`), `supabase/migrations/20260902130000_close_rls_write_leaks.sql:115-120`.
- Evidence:
  - `CREATE POLICY projects_select ON public.projects … USING (((auth.uid() = user_id) OR is_project_collaborator(id)))` — default `min_role` is `'viewer'`, i.e. every accepted role, and RLS is row-level: the whole row is returned, including `client_portal` and `calendar_token`.
  - `client_portal` carries both credentials in clear text (the trigger `portal_set_access_token` writes `accessToken` into the jsonb; `validate-portal-passcode` reads `client_portal.passcode`).
  - The 09-02 freeze trigger deliberately left the column writable by editors: "client_portal is left writable deliberately: an editor legitimately manages portal invites" (migration lines 115-120). So an editor can also rotate or disable the portal.
  - The phase-2 drop (`20260827120000_project_financials_drop_legacy.sql:64-67`) removes the four money columns and nothing else — the credential stays on the row after phase 2. The realtime publication also includes `projects`, so the credential streams to subscribed collaborators on every update.
- Failure scenario: with a viewer's JWT: `GET /rest/v1/projects?id=eq.<pid>&select=client_portal` → `{"accessToken":"…","passcode":"…"}`; then, with the anon key, `POST /rest/v1/rpc/portal_submit_co_approval_signed {"p_portal_id":…,"p_access_token":…,"p_change_order_id":…,"p_decision":"approved","p_signer_name":"<homeowner name>","p_consent_accepted":true,"p_signature_data":"data:image/png;base64,…","p_consent_record":"…"}`. The result is a `change_order_approvals` row and an `audit_trail` entry on the change order that reads "Electronically signed via the client portal (E-SIGN/UETA consent …)" — a legal-evidence record the GC cannot distinguish from a real client signature. Money exposure to viewer/editor is by design; the credential exposure is not, and the field role's promise "no costs or margins" is contradicted by `projects.estimate` etc. until phase 2 (known) and by `field_tickets` (not known).
- Fix: move portal credentials off the row into `portal_credentials (project_id uuid pk references projects on delete cascade, access_token text not null, passcode_hash text, updated_at)` with RLS `owner only` (`exists (select 1 from projects p where p.id = project_id and p.user_id = auth.uid())`) and revoke anon/authenticated SELECT; point `portal_project_for_token`, `portal_sign_contract`, `portal-mark-viewed`, `validate-portal-passcode` and `portal_set_access_token` at it; stop writing `accessToken`/`passcode` into `client_portal` in `ProjectContext.syncProjectToSupabase` and `client-portal-setup.tsx:385-387`. Same shape for `sub_portal_links.access_token/passcode` (already owner-only, so only the hashing applies).
- Effort: M.

### F5 — P1 CONFIRMED — Storage policies bind photos and project files to the *uploader*, not to project membership, so photos and documents added by a collaborator are invisible to the GC and vice versa (silent: the URL resolver swallows the denial)
- Where: production `storage.objects` policies `project_photos_select` (`(storage.foldername(name))[1] = auth.uid()::text`) and `project_docs_select` (`owner = auth.uid()`); `utils/photoUploadCore.ts:180-188`; `contexts/ProjectContext.tsx:59-76` (path built from the session `userId`); `utils/storage.ts:69-91` (`resolvePhotoUrls` "Never throws — an unresolvable path just doesn't appear"); `utils/projectFiles.ts:306` (path `<projectId>/<folder>/<file>`, no user segment); `supabase/schema.sql:3270-3273` (`photos_collab_insert` allows editors; `photos_collab_select` returns rows to every collaborator).
- Evidence: an editor's photo lands at `<editorUid>/<projectId>/<photoId>.jpg`; the owner's `createSignedUrls` for that path fails the SELECT policy (folder[1] ≠ owner uid) and the entry is dropped from the map, so the tile falls back to "whatever local copy it has" — none on the owner's device. For `project-documents`, `Storage.list()` is filtered by the same owner-scoped policy, so the GC's Project Files browser (`app/project-files.tsx`, no role gate) never lists a collaborator's upload.
- Failure scenario: GC invites a foreman as Editor (the only working role today), foreman shoots 40 progress photos from AI Punch / Daily Report; the rows appear in the GC's gallery (RLS on `photos` allows it) with blank images; the homeowner digest and portal snapshot built by the GC carry no images. Latent today (0 collaborators) but it is the main path of the collaboration feature.
- Fix: replace the folder-equals-uid predicate with membership on the project segment. Photos: `USING (bucket_id = 'project-photos' AND public.can_access_project((storage.foldername(name))[2]))` for SELECT (and the same with `'editor'` for INSERT/DELETE), keeping folder[1] = uploader on INSERT so quotas/cleanup stay attributable. Project documents: `USING (bucket_id = 'project-documents' AND public.can_access_project((storage.foldername(name))[1]))` for SELECT/UPDATE/DELETE and — this also closes the cross-tenant plant in the appendix — `WITH CHECK (bucket_id = 'project-documents' AND public.can_access_project((storage.foldername(name))[1], 'editor'))` for INSERT. `can_access_project(text)` already exists and is EXECUTE-granted to `authenticated`.
- Effort: S (one migration), plus a guard: extend `scripts/validate-project-file-urls.ts` (or add `validate-storage-policies.ts`) to parse a committed dump of `pg_policies` for `storage` (see O1) and fail if any bucket the app writes with a project segment has a SELECT policy keyed on `auth.uid()` alone.

### F7 — P2 CONFIRMED — Account deletion leaves the client's and subs' data behind in eight tables that have no FK path, and one entry in the deletion list is dead (`portal_messages` has no `user_id` column, so that delete errors on every run)
- Where: `supabase/functions/delete-account/index.ts:80-96, 262-275, 423-428`; `supabase/schema.sql:1339-1351` (`portal_messages` columns), constraints section (no FK for the tables below); `scripts/validate-account-deletion.ts:55-57` (only matches `REFERENCES auth.users(id)`).
- Evidence (enumerated from schema.sql, not from a list): tables with neither an `auth.users` nor a `projects` FK that hold tenant data — `change_order_approvals` (`signature_data` image, `signer_email`, `consent_record`), `portal_messages` (`author_email`, `body`), `portal_budget_proposals` (`proposer_email`, amounts), `portal_decision_audit`, `sub_submitted_invoices` (`submitted_by_email`, amounts), `notification_outbox` (`recipient_email`, payloads), `memory_embeddings` (plan text; `user_id` with no FK), `conversations` (`participant_ids`). The guard is blind to all of this because it enumerates FKs, and these tables have none (rule 5, in the other direction).
- Failure scenario: a GC deletes their account. Their homeowner's e-signature image, consent record and email survive in `change_order_approvals`; every portal message body and the client's email survive in `portal_messages`; the sub's invoices and email survive in `sub_submitted_invoices`; the GC's own notification payloads survive in `notification_outbox`. The deployed `delete-account` is v2 (2026-05-07) and older than the repo, so today's live behavior is worse than what was audited here.
- Fix: in `delete-account`, before the row pass, delete by the already-collected `projectIds`: `change_order_approvals`, `portal_messages`, `portal_budget_proposals`, `portal_decision_audit` on `project_id in (…)` (text and uuid variants), `sub_submitted_invoices` on `sub_portal_id in (select id from sub_portal_links where user_id = …)`, `notification_outbox` on `recipient_user_id`, `memory_embeddings`/`ai_daily_usage`/`rate_overrides` on `user_id`; remove the dead `'portal_messages'` entry. Migration: `alter table memory_embeddings add constraint … foreign key (user_id) references auth.users(id) on delete cascade` (same for `ai_daily_usage`, `rate_overrides`). Guard: extend `validate-account-deletion.ts` to enumerate every table whose columns include any of `user_id, recipient_user_id, gc_user_id, project_id, portal_id, sub_portal_id` and require either a CASCADE FK or an explicit delete in the function.
- Effort: M.

## Unauthenticated reach — what `anon` can do end to end (one page)

Roles: `anon`/`authenticated` have `rolbypassrls = false`; `service_role` and `postgres` bypass RLS. `authenticator` does not inherit. The `private` schema (holds `cron_auth`) is `postgres`-only; `app_config` (`notify_key` empty, two edge-fn URLs) has RLS with zero policies and anon SELECT explicitly revoked.

Tables — anon holds table-level `INSERT/UPDATE/DELETE` on all 108 (Supabase default) but RLS default-denies; the only rows anon can read are: `cached_bids`, `cached_companies`, `cached_jobs`, `geocode_run_lock` (explicit `TO anon, authenticated USING (true)`), `city_coords` (`TO public USING (true)`), and `assemblies` rows with `is_system = true`. Every other permissive policy carries `auth.uid()`, `auth.jwt()`, `auth.role() = 'authenticated'`, or a `can_access_project`/`is_project_collaborator` call. SELECT is additionally revoked at grant level on `app_config, closeout_binders, portal_snapshots, project_contracts, rate_limit_counters, selection_categories, selection_options, sub_portal_snapshots`; INSERT on `change_order_approvals, portal_budget_proposals, portal_messages, sub_submitted_invoices`. Realtime publication (`supabase_realtime`) carries 11 tables; anon subscriptions receive nothing because the same SELECT policies apply.

RPC — SECURITY DEFINER functions anon can execute (`has_function_privilege` = true), grouped by what guards them:
- Token/uuid in body, verified: `portal_get_snapshot`, `portal_get_snapshot_v2`, `portal_get_messages`, `portal_post_message`, `portal_submit_budget_proposal`, `portal_submit_co_approval`, `portal_submit_co_approval_signed`, `portal_choose_selection`, `portal_sign_contract` (passcode bypass — F3), `sub_portal_get_snapshot`, `sub_portal_submit_invoice`, `submit_prequal_packet`, `lookup_prequal_packet_by_token` (over-returns — F14), `submit_pro_response`, `get_rfi_by_token`, `get_submittal_by_token`, `fetch_shared_schedule` (30-day expiry; writes `last_accessed_at`).
- Oracle-only, low value: `gc_for_portal`, `gc_for_sub_portal`, `gc_user_for_company_slug`, `is_published_portal`, `is_published_sub_portal`, `public_cost_index` (opt-in filtered), `can_view_project_financials`/`is_project_collaborator` (false for anon), `is_email_unsubscribed` (INVOKER; RLS returns false), `consume_rfp_post_credit` (no-op without `auth.uid()`).
- No caller check at all: `portal_mark_item_viewed` (F9), `fire_notify` (F1/F9), `cost_benchmark_stats` (F8), `submit_sub_change_request` (broken — F13).
- Correctly locked to `service_role` (+`postgres`): `award_rfp`, `grant_rfp_post_credit` (09-02 fix verified live: `{postgres=X, service_role=X}` and in-body `auth.role()` guard), `get_portal_snapshot` (legacy, no token), `get_sub_portal_snapshot` (legacy), `match_project_memory`, `portal_project_for_token`, `rate_limit_increment`, `verify_cron_secret`; `ai_*` usage functions are `authenticated` + `service_role` only (their `COALESCE(auth.uid(), p_user_id)` would otherwise let anon meter arbitrary users).
- Trigger functions carrying the `=X` PUBLIC grant (`handle_new_user`, `enforce_free_tier_project_cap`, `notify_*_fn`, `resolve_*`, `recompute_commitment_paid_to_date`, the freeze functions): not reachable — Postgres refuses "trigger functions can only be called as triggers".

Storage: three public buckets (`plan-sheets` 7 objects, `rfp-attachments` 5, `profiles` 0) answer unauthenticated `GET /storage/v1/object/public/…` for anyone holding the path; none has a SELECT policy, so listing is denied (assumed Supabase semantics — see "could not verify"). All other buckets are private; write policies are folder-bound except the three bucket-only INSERT policies noted in the appendix.

Edge functions deployed with `verify_jwt:false` (reach, not audited here): `fetch-external-data, stripe-webhook, notify, notify-nearby-contractors, unsubscribe, daily-digest, geocode-bids, auth-magic-link, homeowner-weekly-digest, coi-expiry-watch, schedule-ical, financing-redirect, financing-callback, seal-document, qbo-connect-callback, portal-mark-viewed, mcp-token, mcp, revenuecat-webhook, public-lead-intake, public-cost-index, widget-estimate`.
