## Findings (ranked; most severe first)

### F1 — [P1] [CONFIRMED] Children created offline in the same session as their project are permanently dropped on flush: the flush runs the parent's group and the children's groups concurrently, the child's RLS policy is evaluated before its FK, and the RLS error is classified terminal.
- Where: `utils/offlineQueue.ts:347-355` (concurrency), `:204-211` (groups are per record, so `projects:P` and `daily_reports:D` are different groups), `:137-147` (`isTerminalError` — `row-level security` and any `violates` that is not `foreign key`), `:306-322` (terminal → drop + drop dependents); `supabase/schema.sql:3045,3061,3270,3406,3446,3466,3570,3588` (INSERT policies on `daily_reports, deliveries, photos, project_financials, punch_items, rfis, submittals, time_entries` all require `can_access_project(project_id, …)`), `:4019` (`can_access_project` = `exists (select 1 from projects p where p.id = pid and p.user_id = auth.uid())`); `contexts/ProjectContext.tsx:1934-1944` (the "FIFO, so enqueuing first = inserted first" assumption).
- Evidence: `const batch = groups.slice(i, i + MAX_CONCURRENCY); const batchResults = await Promise.all(batch.map(processGroup));` — the project upsert and up to four child groups are dispatched in the same tick. Postgres evaluates `WITH CHECK` before constraints and FK triggers, so a child that arrives before the parent commits fails with `new row violates row-level security policy for table "daily_reports"`, which `isTerminalError` returns true for. The queue's own comment (`:130-136`) says FK failures were made non-terminal precisely for this case — but the FK never gets a chance to fire.
- Failure scenario: a super creates a project in the truck with no signal, then on site files a DFR with 3 photos and 2 punch items. On reconnect batch 0 = `[projects:P, daily_reports:D, photos:1, photos:2, photos:3]`. The project upsert is the largest payload; the four small inserts reach Postgres first, `can_access_project` sees no project row, all four are dropped, and their toast reads "4 change(s) couldn't be synced (daily_reports, photos)". The photo *bytes* still upload (separate queue) and become orphaned objects. F3 then erases the local DFR on the next refetch. This is data loss on the app's flagship offline path; I rank P1 only because it needs an offline project *creation* — by the rubric's letter it is P0.
- Fix: in `runOfflineQueue`, run every `projects` (and any table that is a parent of another queued table) group to completion before starting the rest — simplest: `const parents = groups.filter(g => g[0].table === 'projects'); await Promise.all(parents.map(processGroup)); then the remaining batches`. Additionally treat an RLS `WITH CHECK` failure on an INSERT for a table whose policy references `projects` as retryable-once (bump `retryCount`, keep the group) rather than terminal.
- Effort: S

### F4 — [P1] [CONFIRMED] A kill or crash mid-flush re-sends inserts that already landed; the duplicate-key error is classified terminal, the record's dependent updates are dropped as orphans, and the user is told their data "couldn't be synced" when it is in fact on the server.
- Where: `utils/offlineQueue.ts:383-399` (processed ids are removed from the persisted queue **once, after every batch has finished**), `:247-251` (plain `insert`, "upsert here would silently overwrite"), `:137-147` (`m.includes('violates') && !m.includes('foreign key')` → `duplicate key value violates unique constraint` is terminal), `:306-322` (dependents dropped and counted as failed), `:372-374` (toast). Contrast `utils/photoUploadCore.ts:225-233,272-278` where "already exists" is treated as success.
- Failure scenario: offline session queues `insert change_orders:C` + `update change_orders:C (status approved, $7,500)`. Reconnect; the flush has 40 groups (8 batches). The insert commits in batch 1; the OS kills the app in batch 6 before the write-back. Next launch re-sends the insert → `23505 duplicate key` → terminal → the approval update is dropped as an orphan → the server keeps the unapproved CO; the toast says "2 change(s) couldn't be synced (change_orders)". Any long flush after a bad-signal day has this window.
- Fix: in the insert branch, treat a duplicate-key error on INSERT as success (`if (msg includes 'duplicate key') { gProcessed++; continue to next mutation in the group }`); move the write-back inside `processGroup` (remove that group's resolved ids under the queue lock as soon as the group finishes) so the kill window is one group, not the whole flush.
- Effort: S

### F5 — [P1] [CONFIRMED] Project edits are whole-row `upsert`s of a snapshot taken at enqueue time with no version check, so a phone that reconnects replays a stale `schedule`/`estimate`/`client_portal` blob over whatever the web app changed in the meantime.
- Where: `contexts/ProjectContext.tsx:1895-1916` (every column, including `schedule`, `estimate`, `linked_estimate`, `estimate_versions`, `collaborators`, `client_portal`), `:2130` (`updatedAt` is the device clock; `supabase/schema.sql:3659-3710` has no `updated_at` trigger for `projects`), `utils/offlineQueue.ts:103-119` (payload persisted verbatim), `:252-257` (upsert = replace); `hooks/useLiveSchedule.ts:24-35` + `utils/scheduleMerge.ts:22-43` (the 3-way merge only protects two *live* sessions).
- Failure scenario: Sunday night the super changes a project's status offline (queued: full row with Sunday's 60-task schedule). Monday morning the PM re-sequences 12 tasks on the web. Monday afternoon the super's phone reconnects: the queued upsert writes Sunday's schedule back; the PM's browser receives the UPDATE over realtime, `mergeScheduleTasks` sees every task "changed by the peer" and adopts it; the PM's morning is gone on every device with no error. Same for an estimate edited on the web while a phone has any queued project edit.
- Fix: add a server-bumped `version integer` (trigger) to `projects`; queue a *patch* (columns that changed vs the last hydrated snapshot) instead of the full row, and send `update(patch).eq('id', id).eq('version', expectedVersion).select('id')`; on 0 rows, dead-letter the mutation as "changed on another device" (see O1) instead of overwriting. Until then, at minimum strip `schedule`/`estimate*`/`client_portal`/`collaborators` from queued upserts that did not change them.
- Effort: M

## ADD / CONNECT / DO BETTER (ranked by leverage)

### O1 — Dead-letter tray instead of discard — leverage: a GC cannot re-enter what they cannot see; today a dropped write is a toast naming a *table* and a Sentry message with no payload — evidence of the gap: `utils/offlineQueue.ts:155-167` (`oops(\`${count} change(s) couldn't be synced (${tableList})…\`)`), `:372-374`, `:385-399` (dropped entries are simply not written back) — sketch: persist dropped mutations to `mageid_offline_deadletter` (same `OfflineMutation` shape + `reason`) at the write-back; add a "Sync" row in Settings that lists each item as *table · record title · reason* with Retry / Discard; count dead letters in `hooks/useOfflineQueueDepth.ts` and mount `OfflineSyncPill` in every tab header (`app/(tabs)/_layout.tsx`), not only Home. ### O2 — Parent-before-child flush ordering with explicit dependencies — leverage: every offline-created job is a tree — evidence: `utils/offlineQueue.ts:347-355` + `contexts/ProjectContext.tsx:1934-1944` — sketch: add optional `dependsOn?: string` (a record key) to `OfflineMutation`; `supabaseWrite` callers that insert children pass `projects:${projectId}`; `runOfflineQueue` topologically sorts groups so a group runs only after its dependency group finished successfully, and dead-letters it (O1) if the dependency died. Fixes F1 and the ordering half of F12.

### O3 — Per-record version stamps and patch writes — leverage: the "phone offline while web edits" case is the collaboration product's normal day — evidence: `contexts/ProjectContext.tsx:1895-1916` (full-row upsert), `utils/offlineQueue.ts:262-277` (the deliberate no-count decision) — sketch: `version integer default 1` + a `BEFORE UPDATE` trigger that increments it on `projects`, `change_orders`, `invoices`, `daily_reports`, `punch_items`; queued updates carry `expectedVersion` and use `.eq('version', expectedVersion).select('id')`; 0 rows → dead-letter as "changed elsewhere" with both copies so the user can pick. ### O4 — Queue-first writes + idempotent inserts + per-group write-back — leverage: makes the queue the source of truth instead of a fallback that only sees network errors — evidence: `utils/offlineQueue.ts:409-457` (queue only on network failure), `:247-251`, `:383-399` — sketch: `supabaseWrite` = enqueue → attempt → remove-on-ack; treat `23505 duplicate key` on INSERT as success; write back per group. ### O5 — Flush-before-sign-out and flush-on-background — leverage: the two moments field data is most likely to be pending — evidence: `contexts/AuthContext.tsx:608-645`, `app/_layout.tsx:335-341` — sketch: `logout()` awaits both queues; the Settings dialog reads the depth; `AppState` `background` runs `syncDebounceMap` timers immediately and starts a flush (on web `pagehide`).
