## [x] #1 — [submission_blocker] Account deletion hard-fails with an FK violation after the user's data is already wiped — Apple 5.1.1(v) blocker plus irreversible data loss

**Where:** `supabase/functions/delete-account/index.ts:137`

**What breaks:** `sb.auth.admin.deleteUser(userId)` issues a hard DELETE on auth.users. Production introspection (re-confirmed) shows exactly two FKs to auth.users with ON DELETE NO ACTION (confdeltype='a'): project_collaborators_user_id_fkey and project_collaborators_invited_by_fkey. project_collaborators is absent from USER_SCOPED_TABLES (lines 53-65), and its only cascade path is project_collaborators_project_id_fkey -> projects, which fires only for projects the deleting user OWNS. A user who is a collaborator on someone else's project still has a referencing row when the auth delete runs, so Postgres raises 23503, the function returns 500, and AuthContext.deleteAccount (contexts/AuthContext.tsx:670) throws. Steps 2 and 3 — 33 tables of row deletes plus Storage object removal — have ALREADY run as separate non-transactional PostgREST calls with no rollback. The in-file comment at line 50-52 ('missing one just means orphan rows (no functional break)') is factually wrong for NO ACTION FKs.

**User impact:** A Project Manager or Expeditor (two of the five shipped personas, which exist precisely to be invited onto a GC's project) taps Settings -> Delete Account. Their projects, invoices, daily reports, photos, RFIs, punch items and Storage objects are permanently destroyed, then the call 500s and they are told 'Your data was removed but the login still exists. Email support@mageid.app to finish removal.' They are left signed in to a gutted, unrecoverable account. Apple explicitly exercises account deletion during review, so a 5.1.1(v) path that errors is a hard rejection — and it is total loss for the first tester who hits it.

**Fix plan:** Three-part fix, all in one pass. (1) In delete-account/index.ts, before the auth delete at line 137, add two service-role deletes on project_collaborators: `.eq('user_id', userId)` and `.eq('invited_by', userId)` — invited_by is NOT NULL (schema.sql:1297-1308) so the row must be deleted, not nulled. (2) Ship a migration flipping both constraints so the schema is the backstop: `alter table public.project_collaborators drop constraint project_collaborators_user_id_fkey, add constraint project_collaborators_user_id_fkey foreign key (user_id) references auth.users(id) on delete cascade;` and the same for invited_by. (3) Make the sequence failure-safe: move `auth.admin.deleteUser` to the FRONT of the function, or move the whole routine into one SECURITY DEFINER SQL function, so a failure can never leave a half-deleted account. Add a regression test that creates user A, has user B invite A onto B's project, accepts, then calls delete-account as A and asserts 200; plus a schema test that enumerates `pg_constraint where confrelid='auth.users' and confdeltype='a'` and fails if any relation is missing from USER_SCOPED_TABLES.

## [x] #6 — [data_leak] grant_rfp_post_credit is SECURITY DEFINER with no caller check and EXECUTE-granted to anon in production — anyone can mint paid RFP credits into any user's billing row

The body (4205-4227) inserts into rfp_post_payments and upserts rfp_post_credits for whatever p_user it is handed, consulting no caller identity — no auth.uid() comparison, no token, no cron secret. Production introspection re-confirmed just now: has_function_privilege('anon', ...,'EXECUTE') = true and the same for authenticated, i.e. reachable over PostgREST with the anon key that is hardcoded at lib/supabase.ts:18. ## [x] #7 — [data_leak] projects_update lets an invited 'editor' collaborator reassign projects.user_id and permanently steal the project from its owner

**Where:** `supabase/schema.sql:3163`

**What breaks:** Verified verbatim at schema.sql:3163-3165: `CREATE POLICY projects_update ON public.projects FOR UPDATE TO authenticated USING ((auth.uid() = user_id) OR is_project_collaborator(id,'editor')) WITH CHECK ((auth.uid() = user_id) OR is_project_collaborator(id,'editor'))`. The WITH CHECK is satisfied by the first disjunct as soon as the collaborator sets user_id to their own uid, and nothing freezes the column: enforce_free_tier_project_cap is BEFORE INSERT only, and portal_set_access_token / projects_updated_at do not touch user_id. is_project_collaborator (schema.sql:4258) resolves via project_collaborators with status='accepted' and role in ('owner','editor'). Once user_id flips, the original owner fails projects_select's `auth.uid() = user_id` (schema.sql:3161) and is not in project_collaborators, so they lose SELECT on their own row, and projects_delete is `USING (auth.uid() = user_id)` so they cannot even delete it. crew_members explicitly defends against this exact attack with crew_freeze_ownership_columns (schema.sql:3825); projects does not.

**User impact:** A GC invites an outside PM or a partner firm as an 'editor' on one job — the documented Live Schedule Collaboration flow via app/accept-invite.tsx. That collaborator issues PATCH /rest/v1/projects?id=eq.<pid> with {'user_id':'<their own uid>'} using the anon key plus their own JWT. The project transfers irreversibly, including its estimate, its client_portal accessToken and every child row keyed on it. The original owner's project list silently goes from N to N-1 with no error, no audit entry and no client-side recovery.

**Fix plan:** Do not try to fix this in the policy — the owner disjunct is always satisfiable by the row the attacker is writing. Add a BEFORE UPDATE trigger on public.projects modelled on crew_freeze_ownership_columns (schema.sql:3825): `if auth.uid() is not null and auth.uid() is distinct from old.user_id then new.user_id := old.user_id; end if; return new;`. Consider freezing client_portal/access_token the same way. Add a regression test that authenticates as an accepted editor collaborator, PATCHes user_id, and asserts the original owner still owns the row and can still SELECT it.

## [x] #8 — [data_leak] sub_submitted_invoices UPDATE policy's WITH CHECK drops the ownership test — a sub can move a money row into another contractor's books

**Where:** `supabase/schema.sql:3283`

**What breaks:** Verified at schema.sql:3283 and against live pg_policies: `gc updates sub invoices for own portals` is FOR UPDATE TO authenticated with USING = EXISTS(sub_portal_links spl WHERE spl.id = sub_submitted_invoices.sub_portal_id AND spl.user_id = auth.uid()) but WITH CHECK = `(status = ANY (ARRAY['submitted','approved','rejected','paid']))` only. USING is evaluated against the OLD row and WITH CHECK against the NEW row, so the NEW row is never re-checked for ownership: sub_portal_id, project_id, commitment_id, amount and status can all be rewritten to push the row into another tenant. There is no INSERT or DELETE policy on the table, so this UPDATE is the only write surface and it is the unguarded one. Blast radius is amplified by schema.sql:3239 `CREATE TRIGGER sub_invoice_recompute_commitment AFTER INSERT OR DELETE OR UPDATE ... EXECUTE FUNCTION recompute_commitment_paid_to_date()`, which is SECURITY DEFINER (schema.sql:4808) and writes `UPDATE public.commitments SET paid_to_date = ...` for whatever commitment_id was supplied, bypassing RLS.

**User impact:** Any subcontractor who has been emailed a sub-portal link (the id and token are in the URL) and also has a MAGE account can create a throwaway project and portal, mint an invoice via the anon sub_portal_submit_invoice RPC, then PATCH that row's sub_portal_id to the victim GC's portal with {amount: 250000, status: 'paid', commitment_id: '<victim commitment>'}. The victim contractor gets a $250k phantom paid sub invoice on their job (hooks/useSubSubmittedInvoices.ts:78 selects '*' scoped only by RLS), a corrupted commitments.paid_to_date driving their buyout and budget screens, and a fabricated line in their 1099 tax export (app/tax-1099-export.tsx:69). The RPC path deliberately forces status='submitted'; this hole is what lets an outsider set 'approved'/'paid'.

**Fix plan:** Replace the WITH CHECK with the ownership predicate ANDed to the status allowlist: `WITH CHECK (EXISTS (SELECT 1 FROM sub_portal_links spl WHERE spl.id = sub_submitted_invoices.sub_portal_id AND spl.user_id = auth.uid()) AND status = ANY (ARRAY['submitted','approved','rejected','paid']))`. Additionally freeze the immutable columns with a BEFORE UPDATE trigger in the crew_freeze_ownership_columns style — `NEW.sub_portal_id := OLD.sub_portal_id; NEW.project_id := OLD.project_id; NEW.commitment_id := OLD.commitment_id; NEW.amount := OLD.amount;` — since the GC only ever needs to change status and notes_from_gc. Then audit for existing damage: `select i.id from sub_submitted_invoices i join sub_portal_links spl on spl.id = i.sub_portal_id where i.project_id is distinct from spl.project_id;` and recompute commitments.paid_to_date afterwards.
