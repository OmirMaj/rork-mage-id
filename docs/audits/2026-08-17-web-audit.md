# Web audit — app.mageid.app

_2026-08-17. Authenticated production session, ~14 routes. **No screenshots** — the
extension's injector timed out on every attempt including an `example.com`
control, so it is environmental. Everything below is measured from **live
computed styles and geometry**, not seen as pixels. Anything purely pictorial
(overlap, shadows, icon rendering, focus appearance) is UNVERIFIED._

## P0 — Job Costing tells you you are UNDER budget when you are OVER

Henderson: `BUDGET $48K`, `ACTUAL PAID $49K`, `Projected $97K`. The KPI reads
**"UNDER BY $49K"** in green with a down-trend icon, and the banner says
*"On track to finish $49K under budget."*

It is **$49K over**.

`utils/jobCostEngine.ts:293,327` computes `variance = projected − budget`
(positive = over). `app/job-costing.tsx:167` does `variancePositive = variance >= 0`
and labels it `'Under by'` with the success colour. **The engine's own header
comment claims variance "shows up negative" when over — comment and formula
disagree, and the UI trusted the comment.** Also hits the per-phase drilldown
(`:697,714`).

For a product whose entire pitch is knowing your real costs, reporting a 2×
overrun as an underrun is the worst possible failure.

### The same card conceals it twice more

- `jobCostEngine.ts:328-329` wraps both percentages in `Math.min(100, …)`, so
  $49K against a $48K budget displays **"100% of budget"** instead of 102%.
- Every phase reads **"ON TRACK"**, because the $49K actual is all
  `(Uncategorized)` and maps to no phase.

Three independent mechanisms, all hiding the same overrun.

## P0 — Invoice status badge is invisible (the iOS #1 bug class, unfixed here)

`app/invoice.tsx:1874` `sent → {bg: t.info, text: t.info}`; `:1877`
`overdue → {bg: t.danger, text: t.danger}`.

Measured live on "Awaiting Payment": `rgb(21,101,192)` text on `rgb(21,101,192)`
background — **contrast ratio 1.00**, a 108×14 solid blue blob. The hero "Draft"
chip is also 1.00.

`punch-list.tsx` was fixed for exactly this. `invoice.tsx` was never checked.

## P1 — Estimate page titles are invisible in light mode

`heroTitle: '#F4EFE6'` / `heroSub: '#C9C3B8'` are hardcoded light colours drawn
on the light theme background `#FBF8F2`, and the hero has no background of its
own. Measured **1.08:1** for the 28px titles "Estimate" and "Review"; **1.65:1**
for both subtitles. `(tabs)/estimate/index.tsx:109,113`,
`(tabs)/estimate/review.tsx:288,289`.

## P1 — markup leaks into the client-mode hero (INFERRED, not observed)

`review.tsx:187` renders `ESTIMATE · {globalMarkup}% MARKUP` in the hero at
lines 185-190, which sits above the ScrollView and **outside** the `mode`
conditional. Observed rendering live in contractor mode; the client-mode render
was NOT observed, because the Contractor/Client toggle only appears when
`cart.length > 0` and the cart was empty.

Code-certain, observation-pending. Everything else in client mode is correct —
`showTotalsBar` is properly gated, and the shared-proposal token is built from
`clientView` only.

## P1 — stale `buildwise_*` / `tertiary_*` localStorage keys are never cleared

They hold real data (change orders, COIs, contacts, subs), the source has **zero
references** to those prefixes, and `LOCAL_USER_CACHE_KEYS`
(`AuthContext.tsx:33+`) lists only `mageid_*` — so **logout never clears them**.
`buildwise_projects` has already diverged from `mageid_projects`.

`CLAUDE.md` states the rule this violates: any per-user key not in
`LOCAL_USER_CACHE_KEYS` "leaks across tenants on shared devices". The de-branding
renamed the keys and left the old data behind.
