## What was actually wrong

The severe findings were authorisation and state, not features.

- **Account deletion could delete another tenant's data, two different ways.**
  It keyed tenant-scoped deletes on a portal id the client mints, so spoofing a
  victim's id onto your own project deleted their portal messages, e-signed
  change-order approvals, budget proposals and decision audit — under the
  service role, returning `success: true`. After the ownership resolver landed,
  a second route opened: `postgrest-js` quotes an `.in()` value containing
  `,()` without escaping, so `x","<victim id>` splits into two values. Proved
  against live PostgREST with the real client, then closed three ways.
- **The notification service leaked a portal access token.** Any signed-in
  caller could steer a sub-portal token into an email they receive.
- **The offline queue was not bound to a session.** It resolved its bearer at
  send time, so on a shared device one user's queued writes could flush under
  another's login — the tenant boundary `CLAUDE.md` exists to protect.
- **Cost seeds had never reached the server.** Every upsert carried a column the
  table does not have, so PostgREST rejected all of them, the queue retried
  forever with no toast, and production holds zero. The cost book has been
  device-only for every user.
- **Retention was netted on some money surfaces and not others**, so the same
  invoice read as paid on one screen and outstanding on another, and a pay link
  minted for an old balance was still being emailed: "$40,000 due" above a
  button that charged $90,000.

## The reviews earned their cost

Every task was implemented by one agent and attacked by a separate adversarial
reviewer, two to four rounds each. **Four times the fix was the bug:**

1. Dropping `user_id` from the shared-project upsert to stop collaborators
   re-owning a row made every editor write fail `NOT NULL` and be discarded as
   terminal — collaborators could not save anything. The ownership freeze
   trigger was already doing that job.
2. An editor whose `project_financials` read failed stored `estimate: null` and
   echoed it back on the next unrelated edit, nulling the owner's estimate on
   both tables. Two rounds to close.
3. The new session-expiry guard counted rejections per caller, so ten concurrent
   requests on one rotated token signed out a session that had just refreshed
   successfully — in exactly the scenario the guard was written for.
4. The cross-tenant delete came back in a new form after its first fix.

Ten of the new guards were broken deliberately in scratch copies to confirm they
fail. One had been passing for the wrong reason; one test could not fail at all.

## One live ship-blocker found while verifying

The exported bundle still carried `react-native-reanimated`'s JavaScript even
though the app does not declare it: `expo-router` declares it an optional peer,
so bun installs it on every clean install and Metro bundles what *resolves*, not
what `package.json` declares. That JS binds a native module the installed binary
does not have — it is why an earlier build rolled back every OTA silently.
Removing it from `package.json` never fixed this; a clean reinstall puts the
markers straight back. It is now blocked at the Metro resolver, and
`test:native-surface` exports the real bundle on every ship-check.

## Before you deploy

  is **unset in production today and forgeable** — a token derived from the
  public fallback literal was accepted by the deployed function.
- **Migration `20260904100100` before `create-payment-link` / `stripe-webhook`**
  or every payment fails to credit.
- **`marketing/portal/index.html` live before `notify`** or every homeowner
  notification 403s. `marketing/dist/` is stale; regenerate it first.
- **Re-run the financials backfill immediately before the OTA** (runbook step 6).
- Four migrations stay in `supabase/migrations/held/`; a bulk push cannot
