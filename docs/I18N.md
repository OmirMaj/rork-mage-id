# MAGE ID — Spanish (i18n) architecture

Status: DECIDED. **Phase 0 foundation BUILT** (new files only, 2026-09-27): the `i18n/` runtime, formatters,
seed catalogs, `LanguageContext`, `LanguagePicker`, the language screen, the edge reply-language rule and the two
validators. Existing-file changes are handoff patches, not yet applied. Branch `claude/i18n-foundation`, base `2859f55b`.
Companion: [`docs/i18n-glossary-es.md`](./i18n-glossary-es.md) (the reviewed construction glossary + tú/usted rule).

> Founder ask: "I want to be able to make this app Spanish friendly."
>
> What that means here: a Spanish-speaking foreman and an English-speaking owner
> can work the **same job**, each in their own language. The field screens come
> first, then money/office screens. Anything sent **outside** the account (a sub's
> lineup text, a homeowner's portal, email or contract) goes in **the recipient's**
> language, not the sender's.

Every claim below was either measured in this repo (the Hermes probe, string
counts, file reads) or is marked as unverified. Research inputs: TECH lane (Hermes
probe on `node_modules/react-native/sdks/hermesc/osx-bin/hermes`,
hermes-2025-07-07-RNv0.81.0), LANGUAGE lane (glossary sources), SCOPE lane (AST
string inventory, live read-only schema query).

## 0. Hard limits this design obeys

| Limit | How it is met |
|---|---|
| OTA only, no native modules | Pure JS. No `expo-localization` (not in the installed build). The device language is read from RN core modules already linked (§4). |
| Hermes + react-native-web | No `Intl.PluralRules`, `RelativeTimeFormat`, `ListFormat`, `Locale` or `formatToParts`. They are **absent on this Hermes** (probed). Only `DateTimeFormat`, `NumberFormat` and `Collator` are used, and only in ways that give the same output on iOS and the web. |
| Money is integer cents | Formatting only. Spanish money output is **identical** to English: `$1,234,567.89` (§6). |
| English must not regress | In English, `t()` returns the **inline English string at the call site**. It never touches a catalog, so output is byte-identical by construction (§3.4). |
| Storage-hygiene | The local key is `mageid_language`, under the existing `mageid_` prefix in `APP_STORAGE_PREFIXES` (§5). |
| Other runs own the screens | This run adds **new files only**. Existing-file changes are written as handoff patches (§13) and applied by whoever owns the file, after the copy/voice pass releases it. |

## 1. Library decision: a small in-house layer (no i18next, no Lingui)

**Decision:** build it in-house, about 300 lines in `i18n/` plus one context file.
No new dependency.

Evidence:

1. **The Hermes Intl probe decides it.** On the RN 0.81 Hermes binary shipped in
   this repo, `Intl.PluralRules` is `undefined`. So are `RelativeTimeFormat`,
   `ListFormat`, `Locale`, `DisplayNames` and `Segmenter`.
   `NumberFormat.formatToParts` throws on the Apple backend.
   `notation:'compact'` and `signDisplay` are **silently ignored**: `12,500`
   comes out where `12.5K` was asked for.
2. **i18next (26.4.2, ~13.7 KB gz) plus react-i18next (17.0.15, ~10.2 KB gz)**
   resolve plurals through `new Intl.PluralRules(code)`. On this Hermes that path
   catches the error and returns a dummy rule, so **Spanish plurals quietly
   collapse to one form**. That is the kind of bug that works on the web and
   breaks on the phone.
   - The fix would be a polyfill, `@formatjs/intl-pluralrules`, which pulls in
     `@formatjs/bigdecimal`, `intl-localematcher` and locale data. FormatJS's own
     docs recommend `polyfill-force` on Hermes because detection can add seconds
     to Android startup.
   - i18next's typed keys "enumerate every possible key". Its docs warn of OOM and
     TS2589, which is a real risk on the founder's 18 GB Mac, where one `tsc` run
     already takes 3.6 GB.
3. **Lingui (@lingui/core 6.8.0, 2.1 KB gz)** needs a Babel macro in
   `babel.config.js`, an extract/compile step, and, by its own RN tutorial, both
   the `intl-locale` and `intl-pluralrules` polyfills on Hermes. Its
   message-as-key style would also fight the copy/voice rewrite running now.
4. **typesafe-i18n** adds a generator and is 2.8 MB unpacked. **rosetta** was last
   released in 2020.
5. **We only need two languages.** English and Spanish plural rules are six lines
   (§3.3). A proof of `t()`, plurals and money ran under both Hermes and Node with
   identical output:
   `["1 pendiente","3 pendientes","Save","$1,234,567.89","-$1.50"]`
   (`scratchpad/hprobe/mini.ts`).

**Revisit if:** we add a third app language with complex plurals (Arabic, Polish,
Russian), or Hermes ships `Intl.PluralRules`. The plural module takes the same
categories as `Intl.PluralRules` (`one | many | other`), so it can be swapped
without touching the catalogs.

> Note: the task text asked for "plurals via Intl.PluralRules". That is not
> possible on the shipped Hermes, and it is the one place this design overrides
> the brief, on measured evidence.

## 3. The `t()` API

### 3.1 Signatures

```ts
// i18n/types.ts
export type Lang = 'en' | 'es';
export type I18nArea =
  | 'common' | 'field' | 'safety' | 'money' | 'office' | 'schedule'
  | 'settings' | 'auth' | 'ai' | 'outbound' | 'portal' | 'email' | 'nav';
export type I18nKey = `${I18nArea}.${string}`;
export type Vars = Record<string, string | number>;
export interface PluralForms { zero?: string; one: string; many?: string; other: string }

// i18n/core.ts
export function t(key: I18nKey, en: string, vars?: Vars): string;
export function tn(key: I18nKey, count: number, en: PluralForms, vars?: Vars): string; // injects {count}
export function getLang(): Lang;                 // module-level, for utils / ErrorBoundary / edge payloads
export function setLang(l: Lang): void;          // called by LanguageProvider only
export function subscribe(fn: (l: Lang) => void): () => void;

// contexts/LanguageContext.tsx
export function useT(): { t: typeof t; tn: typeof tn; lang: Lang };   // re-renders on change
```

Call sites:

```tsx
const { t, tn } = useT();
<Text>{t('field.dfr.weather', 'Weather')}</Text>
<Text>{tn('field.punch.openCount', open, { one: '{count} open item', other: '{count} open items' })}</Text>
showAlert(t('common.error.saveFailed', 'Could not save. Check your connection and try again.'));
```

### 3.2 Key naming

- Format: `<area>.<surface>.<slug>`, for example `field.dfr.weather`,
  `safety.jha.addHazard` or `money.invoice.status.overdue`.
- Keys are **stable IDs**. When the English changes, the key stays the same, and
  the stale check (§10) flags the Spanish for review.
- The codemod builds the slug from the English (camelCase, at most 4 words). A
  person may rename a key before it merges, never after.
- Shared words (Save, Cancel, Delete, Retry, statuses) go under `common.*` **only
  when the meaning really is identical**. "Pending" as a punch item and "Pending"
  as a CO status are different Spanish words (glossary D3), so they are different
  keys.

**Why the English sits inline** instead of living only in the catalog:

- 438 validators grep source files for English. `daily-report.tsx` alone is
  pinned by 32 and `punch-list.tsx` by 21. Inline English keeps every one of those
  greps green.
- The copy/voice pass (`docs/VOICE.md`) keeps editing English **in place, in the
  screen**, exactly as it does today.
- English output never depends on catalog state.

The en catalog is **generated** from the inline defaults. It is the translator's
source and the parity reference. It is never the runtime source for English.

**Typing:** keys are typed as the template literal `` `${I18nArea}.${string}` ``,
which catches wrong areas and non-namespaced keys at compile time for almost no
`tsc` cost. Key **existence** and **parity** are checked by `validate-i18n`, not
by a giant literal union. A full key union was rejected for three reasons:

- tsc memory (see the i18next warning above);
- merge churn, since six parallel runs would all regenerate one union file;
- it forces a generated-file edit before every new string.

The es catalog is typed as `Partial<Record<I18nKey, EsEntry>>`, where
`EsEntry = { s: string | PluralForms; src: string /* fnv1a32 of the English it translates */ }`.

### 3.3 Plurals (no `Intl.PluralRules`)

```ts
// i18n/plural.ts — CLDR rules, checked against Node ICU 78.2
export function pluralCategory(lang: Lang, n: number): 'one' | 'many' | 'other' {
  if (lang === 'en') return n === 1 ? 'one' : 'other';   // EXACTLY the inline ternaries (see below)
  const a = Math.abs(n);
  if (a === 1) return 'one';
  if (Number.isInteger(a) && a !== 0 && a % 1_000_000 === 0) return 'many';
  return 'other';
}
```

Resolution order in `tn`:

1. exact `zero` when `count === 0` and a `zero` form exists (an explicit override,
   like ICU `=0`, not a CLDR category);
2. `many`, falling back to `other`;
3. `one` or `other`.

`many` exists so that "1 000 000 de dólares" can be written correctly. It is
rarely needed; when absent it falls back to `other`.

**English identity:** the English rule is exactly `n === 1`, the same as the 577
inline `=== 1 ? '' : 's'` ternaries. It deliberately departs from CLDR at -1 (CLDR says
"one", the ternaries print "-1 items"); validate-i18n checks en against ICU for n ≥ 0 and
against the ternary for every n. The codemod converts **only** the
`=== 1` / `!== 1` patterns. Patterns like `> 1` or `>= 2` (which print "0 item")
are left alone and listed for a human, because converting them would change the
English at 0.

### 3.4 Fallbacks and the English guarantee

```
t(key, en, vars):
  lang === 'en'          → interpolate(en, vars)               // byte-identical to today
  lang === 'xx' (dev)    → pseudo(interpolate(en, vars))
  lang === 'es'          → es[key]?.s ?? en                    // missing Spanish → English, never a raw key
                           then interpolate(..., vars)
```

- `interpolate` replaces `{name}` with `String(vars.name)`, the same as a template
  literal `${name}`. An unknown `{x}` is left as-is and flagged by the validator.
  A literal brace is written `{{`.
- Numbers and money are **pre-formatted** by the caller with the existing helpers
  (`formatMoney` and so on). `t()` does no formatting of its own.
- Missing Spanish shows English. It never shows the key and never throws. That is
  what makes a **surface-by-surface** rollout safe.
- **Never call `t()` at module scope.** A constant would freeze the language at
  import time. Module-level label maps (596 of them: `STATUS_LABELS` and the like)
  become functions such as `statusLabel(s, lang?)`. The codemod does this
  conversion and the validator forbids `t(` outside a function body.

### 3.5 Gender and sentence building

- Write Spanish that avoids agreement: "Se guardó {item}" rather than
  "{item} guardado/a". Keyed variants (`{ m, f }`) are allowed only where agreement
  can't be avoided, and they need review.
- **Never build a sentence out of translated fragments.** The 344 `+`
  concatenations and the sentence-building template literals become **one** key
  with placeholders, because Spanish word order differs.
- Utils that build sentences (for example `utils/tomorrowLineup.ts`,
  `groundingChip`, `dailyLogCompletion` and the `*Copy.ts` files) take an optional
  `lang: Lang = 'en'` last parameter. Their pure-function validators keep passing
  unchanged.

## 4. Language resolution

```
explicit choice          profiles.preferred_language (server, once the column exists)
   ↓ else                mageid_language (local AsyncStorage cache of that choice)
device language          iOS:     Settings.get('AppleLanguages')?.[0]         (RN core RCTSettings, linked)
   ↓ else                Android: NativeModules.I18nManager.getConstants().localeIdentifier
                         Web:     navigator.languages?.[0] ?? navigator.language
Intl hint                Intl.DateTimeFormat().resolvedOptions().locale
   ↓ else
'en'
```

- Anything starting with `es` (es, es-US, es-MX, es-419 and so on) maps to `'es'`.
  **Everything else maps to `'en'`.** The app offers two languages. The homeowner
  portal keeps its existing six (§9).
- **The iOS trap:** Hermes's default locale on iOS is matched against the app's
  declared localizations. `app.json` declares none, so a Spanish iPhone probably
  reports `en-*` through `Intl`. That is why `AppleLanguages` sits above `Intl` in
  the chain. It **needs a real-device check** (not yet done), and every step is
  wrapped in try/catch.
- **The device step is gated:** `AUTO_DETECT_DEVICE = false` in `i18n/resolve.ts`
  until the Phase 1 field surfaces are complete. Before then, Spanish is **opt-in
  from Settings only**. Otherwise a Spanish-phone user would land in a half-English
  app they never asked for.
- The choice is made **per user**. The account setting beats the device setting on
  every surface. Procore's mobile app follows the phone instead, and we do better:
  the account setting follows the person across devices.
- Web: the provider sets `document.documentElement.lang` to `'en'` or `'es'`.

## 6. Formatting helpers (`i18n/format.ts`)

**Principle:** Intl on the phone and Intl on the web disagree in Spanish. For
es-US, Hermes/Apple prints `9/27/2026` and `sept 27, 2026`, while browser ICU
prints `27/9/2026` and `27 sept 2026`. So:

- **English:** each helper delegates to exactly the `toLocale*('en-US', opts)`
  call the app makes today, so output is byte-identical on every platform.
- **Spanish:** dates come from our own tables and templates, identical on iOS,
  Android, the web and Deno. `Intl` is never passed an `es-*` locale, except
  `Intl.Collator('es')` for sorting (ñ works on Hermes).

| Helper | en (unchanged) | es |
|---|---|---|
| `formatMoneyCentsL(cents, lang, {decimals=2})` | `$1,234,567.89`, `-$1.50` | **identical to en**. es-US money is US convention. (es-MX gives `USD 1,234,567.89` and plain `es` gives `1.234.567,89 US$`; both are wrong for us.) |
| `formatNumberL(n, lang, decimals)` | `12,500` | identical to en (period decimal, which is the Mexican and US-Spanish convention) |
| `formatDateL(d, lang, 'day')` | `Sep 27` | `27 sept` |
| `'dayYear'` | `Sep 27, 2026` | `27 sept 2026` |
| `'weekdayDay'` | `Sun, Sep 27` | `dom 27 sept` |
| `'long'` | `Sunday, September 27, 2026` | `domingo, 27 de septiembre de 2026` |
| `formatTimeL(d, lang)` | `3:05 PM` | `3:05 p.m.` |
| `relativeParts(ms)` | `{unit, n}`; the call site keeps its own English via `tn` | `hace 5 min`, `hace 2 h`, `ayer`, `hace 3 días` |

Rules:

- **No numeric dates in Spanish.** `9/10` means 9 October to a Mexican foreman and
  10 September to his owner. When `lang==='es'` and the call asked for
  `month:'numeric'`, the helper switches to the month-name style.
- **Money input stays US convention.** `parseLenientNumber` strips commas, which is
  correct for es-US.
- **Money is unchanged by Spanish.** `utils/formatters.ts` `formatMoney` (624 call
  sites) needs **no change** for Spanish.
- **A separate bug found in English, not Spanish work:** Apple's NumberFormatter
  rounds half-to-even. On iOS, `formatMoney(1234.5, 0)` prints `$1,234`, while the
  web prints `$1,235`.
  - `formatMoneyCentsL` avoids it by rounding in integer cents
    (`Math.round` on the magnitude) and formatting the whole-dollar part as an
    integer.
  - Fixing the existing `formatMoney` is an **optional, separate handoff**. It
    changes iOS output (to match the web) only on exact-half inputs. It is not part
    of the Spanish rollout and must not ship silently inside it.
- **Hermes gate:** jest runs on Node ICU and **cannot** see iOS formatting.
  - `scripts/validate-i18n-hermes.ts` bundles `format.ts` and `plural.ts` with
    `bun build --target=browser`, runs them under
    `node_modules/react-native/sdks/hermesc/osx-bin/hermes` and compares against
    golden strings for both languages.
  - It skips with a loud message on a non-Mac host (ubuntu CI) or if the binary is
    missing. The platform is checked, not just the file: the macOS binary ships in
    the npm package on every OS, and running it on Linux would crash, not skip.
  - Wired as `test:i18n-hermes`.

Spanish tables (in `format.ts`):

- months `enero … diciembre`; short forms
  `ene feb mar abr may jun jul ago sept oct nov dic`;
- weekdays `domingo … sábado`; short forms `dom lun mar mié jue vie sáb`.

Main date hook point: `utils/calendarDate.ts` `formatCalendarDay` (hard-coded
`en-US`, imported by 161 files). A handoff patch adds `lang = getLang()` and routes
es through `formatDateL`, which moves 161 files at once with no screen edits.

## 7. AI answers in the user's language

**Rule:** the reply language changes. Nothing else does: not grounding, not honesty,
not schemas.

1. **The client.** `utils/mageAI.ts` gets an optional `lang` (defaulting to
   `getLang()`), sent to the relay as `locale`. This is a hook patch.
   - **Cache blocker, handled in the same patch:** when `lang === 'es'`, the
     `cacheKey` becomes `` `${cacheKey}::es` `` (129 cacheKey sites, fixed once
     inside mageAI).
   - English keys are unchanged, so existing English caches still hit and English
     is byte-identical.
2. **The relay** (`supabase/functions/ai/index.ts`, `sys` at line 269,
   `systemInstruction` at 296). When `body.locale === 'es'`, **append** this rule.
   English requests are untouched.
   > `REPLY LANGUAGE: Write all human-readable text in Spanish for US construction
   > crews (neutral Latin American, tú). Keep EXACTLY as given: JSON keys, enum
   > values, IDs, numbers, dollar amounts, dates, units, CSI codes, building-code
   > citations (e.g. IRC R602.3), product and company names, and any quoted source
   > or evidence text. Use these terms: <glossary block>. If unsure of a trade term,
   > add the English in parentheses. If you are drafting a message to be sent to a
   > sub, client or homeowner, use usted. All honesty rules above still apply: never
   > invent data to fill a Spanish sentence.`
   - The glossary block is generated from `docs/i18n-glossary-es.md` core terms by
     `i18n-sync-edge`, capped at about 60 terms to bound prompt size.
3. **Structured output stays English.** zod schemas and enums don't change, so
   client parsing, grounding chips, honesty labels and `requireTier` metering are
   unaffected.
4. **Grounding and honesty labels are catalog strings, not AI output.**
   - Examples: the grounding chip, "Estimated — no learned data yet", "AI draft —
     check before sending", "SIMULATED WEATHER — NOT A FORECAST".
   - These are translated by humans in the catalog (`ai.*`). The model is never
     asked to produce them.
5. **Dedicated AI functions** take `locale` in the body and append the same rule:
   - safety-generate-jha, safety-draft-incident, safety-detect-hazards (field,
     Phase 1);
   - construction-answer (Anthropic), homeowner-weekly-digest, portal-ask-home,
     analyze-photos narrative (Phase 2).
6. **Safety filters must learn Spanish before Spanish output reaches them. This is
   a hard gate.**
   - **Homeowner digest:** `homeowner-weekly-digest` `PAYMENT_RE` (line 252) is
     English only. Add `pag(o|ar|ue|ó)`, `efectivo`, `cheque`, `dólar(es)?`,
     `transferencia`, `depósito`, `factura`, `saldo`, `anticipo`, `reembolso`,
     `cuenta bancaria`, `debe(s|n)?` and `recargo por mora`. Spanish digest output
     stays off until this lands.
   - **Plan sweep:** `utils/plans/planSweep.ts` `FORBIDDEN_WORDS` must add
     `viola\w*`, `incumple\w*`, `no cumple`, `ilegal` and `infracción`.
   - **The `\b` trap:** in JS, `\b` treats accented letters as non-word
     characters, so `\bdólares\b` fails. Use `(?<![\p{L}])…(?![\p{L}])` with the
     `u` flag.
7. **Voice.** `transcribe-audio` forwards to `toolkit.rork.com/stt/transcribe/` with
   **no language parameter**.
   - Spanish accuracy is **unknown**. Test it with real Spanish field audio before
     anything promises Spanish dictation.
   - The voice parsers (`voiceDFRParser` and others) are AI-based. Their prompts
     gain: "the transcript may be Spanish or mixed Spanish/English; write field
     values in {lang}".
   - The Copilot regex shortcuts (`utils/copilot/intentTable.ts`,
     `copilot/schedule/dateSignal.ts`) are English only. Spanish falls through to
     the AI classifier. That works, but it is slower.
   - Spanish date words are Phase 2. Note that `mañana` means both "tomorrow" and
     "morning", so read it in context.
8. **Language of stored records.**
   - Store exactly what the author wrote, in their language. Never translate
     silently.
   - Phase 2 adds a "Translate" action on read. It is labelled
     `Traducido del inglés por IA` / `Translated from Spanish by AI`, with the
     original one tap away, consistent with the brain-center honesty directive.
   - Templates (schedule, punch, toolbox) insert in the creator's language.

## 10. Extraction playbook

### 10.1 When

- One surface at a time, **only after** copy/voice and the file's owning run
  release it (see the owned-file lists).
- Field surfaces go first.
- Never migrate a file another run is editing.

### 10.2 Codemod (`scripts/i18n-codemod.ts`)

Built on `@babel/parser`, `@babel/traverse` and `@babel/generator`, which are
already installed. ts-morph is too heavy on memory. It works one file per run and
writes a diff plus a report. Nothing is committed without review.

It extracts:

- `JSXText` inside `<Text>` and the Text-like components. The string is normalised
  with **Babel's own JSX whitespace rule** (`cleanJSXElementLiteralChild`), so the
  inline English equals what React rendered before.
- String-literal props: `title`, `label`, `placeholder`, `subtitle`, `description`,
  `emptyText`, `hint`, `accessibilityLabel`, `accessibilityHint`, `confirmText`,
  `cancelText`.
- `showAlert(...)` and `Alert.alert(...)` title, message and button text.
- `Stack.Screen` / `options={{ title }}`.
- Module-level label maps. These become functions (`labelFor(x, lang)`) so nothing
  calls `t()` at import time.
- `=== 1 ? '' : 's'` and `n === 1 ? 'x' : 'y'` ternaries, which become `tn`.
- Sentences built with `+` or template literals, which become one key with
  `{placeholders}`. The placeholder names come from the expression (`count`,
  `name`, `date`), falling back to `v1`, `v2`.

It skips, and **reports for a human**:

- plural tests other than `=== 1` / `!== 1`;
- fragments the codemod can't join into one sentence;
- strings that mix user data into grammar;
- anything in the "never translate" column of §8;
- regexes, SQL, URLs and emails;
- `'en-US'` number formatting, which is left alone because it is already correct
  for Spanish.

It marks as `LEGAL_PINNED` (extracted for display, translated only by a human legal
translator): `lienWaiverForms.ts`, contract clauses in `contractEngine.ts`, the
text around AIA forms, and payment and consent terms.

Its output per file: the edited file, the new `en.generated.ts` entries, and a
`scratchpad/i18n-report/<file>.md` listing everything skipped and why.

### 10.3 After the codemod

1. `scripts/i18n-extract.ts` regenerates `en.generated.ts`.
2. The Spanish is written, drafted by AI with the glossary in the prompt and then
   **reviewed by a bilingual construction person**. Each entry stores
   `src: fnv1a32(english)`.
3. `bun run test:i18n` and `test:i18n-hermes` run, along with the file's existing
   validators, which must still pass untouched, and the slick3 visual goldens in
   English, which must be unchanged.
4. The file is marked `migrated` in `i18n/surfaces.ts`. From then on, the no-raw-literal
   guard applies to it.

### 10.4 Text expansion (Spanish runs 20–30% longer)

- There are 808 `numberOfLines={1}` and 383 uppercase labels.
- On migrated screens, prefer wrapping to truncating. Tab and sidebar labels get
  Spanish forms of 10 characters or fewer, chosen in the glossary (for example
  "Inicio", "Obras", "Campo").
- Check every migrated screen in the pseudo-locale (§11) at phone width before
  translating it.

### 10.5 Translator handoff

- `scripts/i18n-export.ts` writes XLIFF 2.0 or JSON, one unit per key, following
  Stripe's localization format.
- Each unit carries: key, English source, `note` (the screen, what the string is,
  the character budget), the glossary terms it contains, and `LEGAL_PINNED` if set.
- The import step validates placeholders and plural forms before writing.

## 11. Validator (`scripts/validate-i18n.ts` → `bun run test:i18n`)

Fails the build when:

1. **Parity:** every `t()`/`tn()` inline English equals `en.generated.ts[key]`,
   meaning extract was run.
2. **Duplicates:** the same key appears with different English at two call sites.
3. **Orphans:** an es key doesn't exist in en.
4. **Placeholders:** the set of `{name}` placeholders differs between en and es,
   or a placeholder is passed that the string doesn't use.
5. **Plurals:** a `tn` key's es entry lacks `one` and `other`, or a `t` key is
   given plural forms.
6. **Module scope:** `t(`/`tn(` is called at module scope, or a string is built
   from translated fragments.
7. **Coverage:** a surface marked `complete` in `surfaces.ts` has any key with no
   Spanish.
8. **Raw literals:** a file marked `migrated` contains raw user-facing JSX text or
   string props (the same AST rules as the codemod, in the style of
   `validate-app-slop.ts`).
9. **Glossary lint on es text:**
   - Spain forms: `vosotros`, `-éis`/`-áis` verb endings, `hormigón`,
     `fontanero/fontanería`, `ordenador`, `móvil`, `vale`, `coger`, `pulse`.
   - `estimación` used for "estimate" (allowed only in keys under
     `money.payApp.*`).
   - `bitácora`.
   - `equipo` in a `*.crew.*` key.
   - usted forms in in-app keys, or tú forms in `outbound.*`, `email.*` or
     `portal.*` keys.
10. **Legal:** a `LEGAL_PINNED` key has es text without a `reviewedBy` field.

It warns (and fails under `--strict`, which a phase release runs) when a stale
translation is found: `fnv1a32(en)` differs from `es[key].src`. This is expected
while copy/voice keeps editing English. The stale Spanish still shows, because a
copy tweak rarely changes meaning, but it is listed for re-review.
`safety.*` keys are always strict, because a safety instruction that drifted in
meaning must not ship.

**The pseudo-locale `xx`** (dev builds and a hidden Settings toggle only; never a
user choice):

- every letter is accented (`Save` becomes `Ŝàvé`) and the string is padded by
  about 35% and bracketed, for example `[Ŝàvé ·····]`;
- `{placeholders}` are left intact.

Any plain-ASCII text on screen was never extracted. Any clipped bracket is a
truncation bug. It exercises the 808 `numberOfLines={1}` sites before any real
Spanish exists.

## 14. Key decisions (summary)

1. **In-house i18n layer.** No i18next or Lingui. Hermes has no `Intl.PluralRules`,
   and i18next plurals silently collapse without it.
2. **`t(key, english, vars)` with the English inline.** In English it returns the
   inline string, so output is byte-identical, the 438 source-grep validators stay
   green, and copy/voice keeps editing English in place.
3. **Hand-written plural rules** for en and es (`one` / `many` / `other`, plus an
   explicit `zero`). The codemod only converts `=== 1` ternaries.
4. **Spanish dates from our own tables, never numeric.** Money and numbers are
   identical to English (es-US convention), so `formatMoney` needs no change for
   Spanish.
5. **Language order:** account setting, then local cache, then the device
   (`AppleLanguages` / `I18nManager` / `navigator`), then Intl, then English. Device
   auto-detect stays off until Phase 1 is complete.
6. **Storage:** `mageid_language`, device-scoped. A migration adds
   `preferred_language` to profiles, subcontractors, crew_members and contacts
   before Phase 1. The homeowner's language already exists.
7. **AI:** a `locale` hint appends a reply-language rule. Schemas, enums, numbers,
   citations and quoted evidence stay verbatim. Honesty and grounding labels are
   human-translated catalog strings. The cache key gets `::es`. Spanish safety
   filters are a hard gate.
8. **Outbound uses the recipient's language** and defaults to English. In-app text
   uses tú; outbound uses usted; contracts use the third person.
9. **Legal text is never machine-translated.** Statutory waivers stay English with
   a Spanish courtesy copy, and contracts need a human legal translator plus
   counsel.
10. **Field first, then money/office, then legal, then the long tail.** Everything
    through Phase 3 ships over the air. The only native item is the Spanish
    permission prompts.
