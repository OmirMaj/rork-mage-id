# Privacy Policy Versus The Code

For the founder's attorney. Written 2026-10-09 (lane PROTECT-SERVER) by reading `marketing/privacy.html` (last updated October 4, 2026) against the code on branch `claude/protect-server`. Not legal advice.

Nothing in `marketing/privacy.html` or `marketing/terms.html` was edited. A change to either page must also change its version and fingerprint in `utils/legalAcceptanceCore.ts` (`PRIVACY_VERSION`, `PRIVACY_TEXT_SHA256`, `TERMS_VERSION`, `TERMS_TEXT_SHA256`); `scripts/validate-legal-acceptance.ts` fails the build otherwise.

Each row: what the policy says, what the code does, and a plain sentence that would be true. "Missing" means the policy is silent.

## Posting Photos And Drawings: What Stays Exposed

After both attachment migrations are applied (the read rule, then the flip), the anonymous permanent link is gone. These remain, and the policy sentence in row 13 is written to be true with them:

- **Any signed-in account can list every posting row** (title, scope, city, and the stored file values): `public_bids_select` is `TO authenticated USING (true)`. Sign-up is self-serve, so "signed-in account" means anyone with an email address. Hiding the browse screen (`RFP_BROWSE_ENABLED = false`) hides a screen, not the table.
- **Any signed-in account can read the files of every OPEN posting.** That is the marketplace's rule (an open posting is shown to contractors), and nothing verifies that an account is a contractor.
- **A caller of the Storage API chooses how long its link lives.** The app asks for one hour. Someone calling the API with their own session can ask for a link that lasts years, for any file they are allowed to read at that moment, and that link keeps working after the posting closes.
- A link signed before a posting closed works until it expires.
- After a posting closes, only its owner and the awarded bidder can sign a link. A bid placed on a closed posting, a declined bid and a withdrawn bid open nothing (`can_read_rfp_attachment`; proved in `scripts/pgq/rfp-attachments-private.mjs`).

**Proposed next tightening (not built; a product decision).** Either of:

1. Narrow `public_bids_select` so a posting row is visible only to its owner, to accounts that have bid on it, and to accounts with a verified contractor profile in the posting's area.
2. Keep the rows visible and hide the files until a contractor is verified: the read rule's open branch gains "and the caller has a verified profile".

And, to take the lifetime choice away from the caller: serve the files through an edge function that signs for a fixed short time, and drop the client's read policy.

## Which Words: The Archive

`docs/legal/versions/` holds the exact text each acceptance hash was taken over, one file per version (`<kind>-<version>-<first 8 of the hash>.txt`), written by `scripts/archive-legal-text.ts`, the same script that computes the hash. `shasum -a 256` of a file there prints the `text_sha256` stored in `legal_acceptances`. The build fails if the file for the current version is missing or does not hash to the constant.

The hash is of the file in this repository (`marketing/terms.html`, `marketing/privacy.html`), the words inside `<main>` with the markup removed. The live site at mageid.app is published from that folder: Netlify deploys it on a push to `main`. Nothing fetches the live page and compares it, so "the words a person saw" equals "the words that were hashed" only if the site was deployed from the commit that carried the constants. When Netlify builds are paused and the site is deployed by hand, deploy from `main`.
