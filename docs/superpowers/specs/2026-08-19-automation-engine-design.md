# Automation engine — design spec (first vertical)

_2026-08-19. Founder vision: every feature is connected automation, not an
isolated tool. This spec locks the interfaces for the first vertical —
**inspection/permit scheduling** — which proves the whole pattern end-to-end and
leaves a reusable engine every other feature plugs into. Approved direction:
build both tracks; zoning grounded **trust-but-verify**._

## Principle (non-negotiable)

Automation must never present a guess as truth. Every derived value (zoning, code
requirement, lead time) carries provenance and, where it drives real work, a
**confirm gate**. Auto-created work lands in **draft**, gated by the existing
autonomy ladder (earned trust, never silent). This is the rate-provenance-chip
discipline applied to scheduling.

## What we reuse (already production-grade — do NOT rebuild)

- `utils/scheduleEngine.ts` / CPM: real dependencies with `lagDays` across FS/SS/FF/SF. "Give it a week" IS `{ type: 'FS', lagDays: 7 }`.
- `utils/permitRoadmap.ts`: roadmap inspections already carry `gatesTaskHint` + `leadTimeDays` + `bookByDate()`.
- The autonomy ladder (`utils/brain/*`, `hooks/useAutonomy`): draft + earned-trust + provenance.
- Event-watcher pattern in `ProjectContext` (CO→reflow, DFR→progress) — the proven template for "event → connected work".

## Components (each isolated, testable, one purpose)

1. **`utils/automation/leadTimeLibrary.ts`** — pure data + lookup. `getLeadTime(kind, jurisdiction?) → { days, source: 'default'|'jurisdiction'|'learned', confidence }`. Seeded defaults (DOB inspection ~7–10 d, permit review ~30 d, submittal ~14 d, RFI ~7 d). No I/O. Learnable later via the prediction ledger; v1 is static defaults + provenance.
2. **`utils/automation/eventToScheduleWork.ts`** — the FACTORY (pure). Input: a `ScheduleWorkRequest` (gatingTaskId or gatingTaskHint, kind, leadTimeDays, whoActs, sourceEventRef). Output: a **draft** `ScheduleTask[]` linked as predecessor/successor with the lag, marked `isAutoGenerated`, carrying `sourceEventRef` for audit + idempotency. No side effects — returns tasks the caller commits. Idempotent on `sourceEventRef` (never double-creates).
3. **`types` additions** — `ScheduleTask.isAutoGenerated?`, `ScheduleTask.sourceEventRef?` (feature+id), and a structured `Project.structuredAddress?` `{ street, city, state, zip, county?, parcelId?, zoningDistrict?, zoningConfirmedAt?, zoningSource? }` (additive; `location` free-text stays as fallback).
4. **`utils/automation/jurisdiction.ts`** — trust-but-verify zoning. `resolveZoning(project) → { district, source: 'guess'|'confirmed', confidence }`. v1: geocode (existing Nominatim) + a best-guess (leave the guess source pluggable — AI or a future parcel API), NEVER auto-confirmed. Downstream code requirements + auto-schedule are BLOCKED until `zoningConfirmedAt` is set.
5. **Roadmap→schedule adapter** — turn each `RoadmapInspection` (gatesTaskHint + leadTimeDays) into a factory `ScheduleWorkRequest`, produce draft tasks, present them in a **review sheet** ("These 6 inspections will be added to your schedule; confirm"). On confirm, commit via existing schedule mutation + CPM recompute. Nothing auto-commits.
6. **Confirm-gate UI** — a small "Confirm zoning: **R-5**? (we guessed from the address)" affordance on the project + the roadmap. Until confirmed, code/auto-schedule features show "confirm zoning to enable".

## Data flow

address → `jurisdiction.resolveZoning` (guess, provenance) → **contractor confirms** →
roadmap inspections (grounded by jurisdiction) → `eventToScheduleWork` (draft, lag from
`leadTimeLibrary`) → **review sheet** → contractor confirms → commit → CPM cascade → audit.

## Error handling / honesty

- No zoning confirmed → downstream blocked, not guessed.
- Factory can't resolve a gating task → returns the task as `anchorType: 'SNET'` on the computed book-by date with a "couldn't link — pick a predecessor" flag (never silently floats).
- Every auto-task carries `sourceEventRef`; re-running the roadmap never duplicates (idempotent).
- Lead times show their `source`/`confidence` (default vs jurisdiction vs learned).

## Testing

- `leadTimeLibrary`: pure unit (validator script) — every kind returns a positive lead + provenance.
- `eventToScheduleWork`: pure unit — lag applied correctly (FS+lag), idempotent on sourceEventRef, unresolved-gate path anchors on book-by date. Add to ship-check.
- Render coverage: mount the review sheet with a seeded roadmap; assert draft tasks render + nothing commits without confirm.
- Zoning: confirm-gate blocks downstream until confirmed (unit + render).

## Decomposition (agent-buildable units, built against these interfaces)

Buildable in parallel once the types + factory signature are fixed:
- A: types additions + `leadTimeLibrary` (+ validator).
- B: `eventToScheduleWork` factory (+ validator, break-tested).
- C: `jurisdiction` + structured address + confirm-gate model.
- D: roadmap→schedule adapter + review sheet UI (depends on A/B interfaces).
- E: render-coverage tests for the review sheet + confirm gate.

## Out of scope (later verticals, Track 3)

RFI/submittal/material-lead-time/milestone triggers reuse the SAME factory once
this vertical proves out. AHJ inspection-submission/polling APIs are a separate
integration. Nationwide parcel-API grounding upgrades the "guess" source behind
the confirm gate without changing the spine.
