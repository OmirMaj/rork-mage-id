MIGRATION (file `supabase/migrations/20260725120000_brain_predictions.sql`; applied ONLY via Supabase MCP apply_migration, project nteoqhcswappxxjlpvap):
```sql
create table public.brain_predictions (
  id uuid primary key,
  user_id uuid not null references auth.users(id) on delete cascade default auth.uid(),
  project_id text,
  kind text not null check (kind in (
    'pace_suggestion_applied','delay_ripple_applied','leak_flag',
    'estimate_confidence_snapshot','judges_verdict','instant_bid_sent',
    'bid_score','leveling_adjustment')),
  subject_id text not null,
  payload jsonb not null default '{}'::jsonb,
  predicted_at timestamptz not null default now(),
  resolved_at timestamptz,
  outcome jsonb
);
alter table public.brain_predictions enable row level security;
create policy brain_predictions_owner on public.brain_predictions
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());
create index brain_predictions_user_kind_open
  on public.brain_predictions (user_id, kind) where resolved_at is null;
create index brain_predictions_user_subject
  on public.brain_predictions (user_id, kind, subject_id);
```

4. THE 3 RISKIEST DESIGN DECISIONS
──────────────────────────────────────────────
D1 — Prediction storage: Supabase table vs AsyncStorage vs riding domain objects.
RECOMMEND: the `brain_predictions` table. Grounding is decisive: AsyncStorage per-user keys are wiped on every sign-in (AuthContext — a months-horizon ledger cannot live there), and domain-riding can't home judges_verdict/bid_score/leveling (no synced parent). Risks accepted + mitigated: schema-before-OTA ordering (queue now re-queues PGRST schema misses without burning retries — verified :49-66); duplicate rows from re-capture (systemically neutralized by earliest-wins `dedupeBySubject` at read time, never trusted at write time); one new RLS surface (single owner-only policy, no edge fn, writes only via the mandated queue).

D2 — Where One Mind lives: upgrade ask.tsx vs new screen vs copilot capability.
RECOMMEND: upgrade ask.tsx in place, keep mageAgent's buildBusinessContext as the always-present RECORDS block, add the copilot-hub question-shaped handoff. The capability contract (draft→gaps→apply) structurally cannot host Q&A; a fourth conversational surface reproduces the audited anti-pattern; and the RECORDS-block floor guarantees the swap can only deepen answers, never regress them — every engine block is additive try/catch, so a failing engine degrades to exactly today's behavior. This also makes B7 a low-risk bundle despite touching the flagship surface.

D3 — Grading trigger: event hooks vs background/server jobs vs on-demand sweep.
RECOMMEND: hybrid client-side — (a) deterministic in-context hooks at the two moments that matter (CO-approved → leak grading, in the exact ProjectContext block that already runs one-shot transition side effects; close-project → full-project grade), plus (b) a once-per-session idempotent lazy sweep (useBrainGrading in BrainWatchCard), idempotence guaranteed by `resolved_at is null` filtering. REJECTED: expo background tasks (no TaskManager in the native build — would break the "no native rebuild" constraint) and a server cron grader (would force duplicating pace/estimate/CPM pure engines into Deno and give the edge fn read access it doesn't need). Accepted consequence: grading latency = next app open — irrelevant for a system whose claims resolve over weeks and whose credibility surface gates on n≥3 anyway.
